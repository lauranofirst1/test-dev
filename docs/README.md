## 기획 파이프라인

```
STEP 1  기획안 작성      → 관광 데이터 보며 수정, 사전 진단 (01 §5.2~5.4)
STEP 2  행사 세부 설계    → 지도·부스·QR체험·동선 → 예산/인력 (04, 05)
STEP 3  운영·안전 계획    → 시간표·교대·위험요소·KPI (01 §5.7)
STEP 4  최종 기획서       → 12개 섹션, 계속 수정 가능 (01 §5.8)
        ─────────────
        행사 당일        → 운영 대시보드, QR 지급 (01 §7~10)
        행사 후          → 사후 성과 리포트 (01 §5.9)
```

사전 진단은 단계가 아니라 **상시 도구**입니다. 어느 단계에서든 열 수 있고,
단계가 진행될수록 진단이 쓰는 데이터의 정확도가 올라갑니다.

## 읽는 순서

처음이라면 `00` → `01` 순서로 읽으세요.
구현을 시작한다면 `02`(스키마 먼저 확정) → `03`(계약) → `01`(화면 동작) 순서가 효율적입니다.
`04`·`05`는 해당 화면을 만들 때 펼쳐 보는 상세 문서입니다.

## 기술 전제

- 백엔드: Python + FastAPI + SQLAlchemy, 서비스 로직은 `services/*.py`에 분리(HTTP route에는 계산·검증 로직을 두지 않음)
- DB: PostgreSQL 15+ (개발 환경도 동일 — SQLite는 부분 인덱스·enum·jsonb 동작이 달라 제외)
- 프런트: 외부 차트 라이브러리 없이 CSS 막대로 시각화
- 외부 연동: 한국관광공사 AreaTarDemDsService, KorService2
- AI/LLM은 사용하지 않음 — 모든 진단·추천은 설명 가능한 규칙 기반

## 핵심 원칙

1. **집계 대상은 지급 시점에 고정한다** — 부스·미션·캠페인을 나중에 바꿔도 과거 수치는 변하지 않음
2. **삭제하지 않는다** — 전부 아카이브. 물리 삭제는 운영 CLI에서만
3. **점수는 재현 가능해야 한다** — 진단마다 입력 스냅샷 + 채점표 버전 + 관광 데이터 스냅샷을 저장
4. **측정하지 않은 것을 측정했다고 말하지 않는다** — 참여 proxy를 방문객·혼잡도로 표현하지 않음
5. **동시성 규칙은 DB 제약으로 건다** — 중복 지급 방지를 애플리케이션 코드에만 두지 않음
6. **참여자는 스스로 완료할 수 없다** — 스태프 확인 또는 30초 회전 QR이 현장을 증명함
