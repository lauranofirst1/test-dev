# 부스 QR 체험 화면 `/festivals/{id}/booths/{bid}/experience`

행사장 설계(04)에서 부스에 **QR 체험존 사용**을 켜면 이 화면이 열립니다.
참여자가 부스 QR을 찍었을 때 폰에 뜨는 화면을 부스마다 다르게 꾸미는 곳입니다.

부스마다 다루는 체험이 다르다는 것이 이 기능의 핵심입니다.
체험 부스는 퀴즈, 먹거리 부스는 사진 인증, 관광안내소는 안내 열람처럼
성격에 맞는 상호작용을 붙입니다.

---

## 1. 구조: 테마는 부스, 체험은 미션

| 대상 | 무엇을 정하나 | 저장 위치 |
|---|---|---|
| 부스 | 화면의 **생김새** — 커버 이미지, 색, 인사말, 완료 문구 | `booths.experience_theme` |
| 미션 | 화면의 **동작** — 어떤 체험을 어떻게 통과하나 | `missions.experience_type` + `experience_config` |

한 부스에 미션이 여러 개면 스캔 후 미션 목록이 뜨고, 하나를 고르면 그 체험이 시작됩니다.
미션이 하나뿐이면 스캔 즉시 그 체험으로 들어갑니다(중간 선택 화면 생략).

---

## 2. 테마 편집 (부스 단위)

| 필드 | 설명 |
|---|---|
| 커버 이미지 | 상단 배너. 업로드 또는 축제 기본 이미지 |
| 강조 색 | 버튼·배지 색. 대비비 4.5:1 미만이면 저장 시 경고 |
| 인사말 | "막국수 체험존에 오신 걸 환영합니다" |
| 완료 문구 | 지급 직후 표시 |
| 부스 소개 | 선택, 최대 300자 |

우측에 **실시간 폰 미리보기**를 둡니다. 저장 없이 즉시 반영됩니다.

접근성 기본값을 강제합니다. 강조 색을 어둡게 골라도 본문 텍스트는 항상 대비를 확보하고,
체험 진행 상태를 색으로만 구분하지 않습니다. 야외 축제에서 직사광선 아래 폰 화면을 본다는
전제를 두었습니다.

---

## 3. 체험 유형 (미션 단위)

### v1 — 이번 범위

| 유형 | 참여자가 하는 일 | 완료 판정 | 적합한 부스 | 상태 |
|---|---|---|---|---|
| `stamp` | 도착 확인 버튼 1회 | 즉시 | 순회 스탬프 포인트 | ✅ |
| `quiz` | 객관식 문제 풀이 | 정답이면 완료 | 체험·전시·교육 | ✅ |
| `info` | 안내 콘텐츠 열람 후 확인 | 확인 시 완료 | 관광안내소, 지역상점 | ✅ |
| `photo` | 사진 촬영·업로드 | 업로드 성공 시 완료 | 포토존, 먹거리 | ⛔ §6 |
| `survey` | 짧은 설문 응답 | 제출 시 완료 | 만족도 수집 | ✅ |

`photo` 는 저장 시 `EXPERIENCE_TYPE_UNSUPPORTED` (422) 로 거절합니다.

**`survey` 는 열려 있습니다.** §6 이 사진과 설문을 함께 묶었지만, 같은 절이
설문에 대해서만 "참여 응답은 참여 코드와만 연결되며 별도 신원 정보를 수집하지
않습니다" 라고 못박습니다. 그 약속을 지키는 방법은 하나뿐입니다 —
**자유 서술을 만들지 않는 것.** 문항 유형을 `rating` 과 `choice` 로만 두고,
`type: "text"` 는 422 로 거절합니다. 자유 입력을 열면 사람들이 이름·연락처·민원을
적고, 그 순간 이 기능의 수집 범위가 완전히 달라집니다.

문항은 최대 5개입니다. 부스 앞에 서서 답하는 설문이라 길면 아무도 끝내지 않고,
중간에 그만두면 참여 자체가 완료되지 않습니다. 평점 척도는 2~7 입니다 —
7 을 넘으면 사람이 구간을 구분하지 못해 답이 가운데로 몰립니다.

리포트의 만족도는 평점 문항만 5점 만점으로 **정규화해** 평균 냅니다.
5점 척도와 7점 척도를 그대로 섞으면 7점 문항이 저절로 높은 값이 되어 결과가
그쪽으로 끌려갑니다. 선택 문항은 순서가 없는 값이라 평균에 넣지 않습니다.
조용히 저장해 두면 운영자는 설정한 줄 알고, 현장에서 아무것도 뜨지 않습니다.
§6 의 개인정보 처리(동의·보관·삭제)가 정해지면 엽니다.

**설정 항목**

```jsonc
// quiz
{
  "question": "춘천 막국수의 주재료는?",
  "choices": ["메밀", "밀", "쌀", "감자"],
  "answer_index": 0,
  "max_attempts": 3,
  "hint": "겨울에 잘 자라는 곡물입니다"
}

// photo
{
  "guide_text": "포토존 간판이 나오게 찍어주세요",
  "max_bytes": 8000000,
  "consent_required": true
}

// survey
{
  "questions": [
    { "type": "rating", "text": "부스 만족도", "scale": 5 },
    { "type": "choice", "text": "어떻게 알고 오셨나요?", "choices": ["SNS", "현수막", "지인", "우연히"] }
  ]
}

// info
{
  "body": "춘천 소양강 스카이워크는 도보 15분...",
  "links": [{ "label": "관광 코스 보기", "url": "https://..." }],
  "min_dwell_seconds": 5
}
```

`quiz`의 `answer_index`는 **참여자 응답에 절대 내려가지 않습니다.**
채점은 서버에서만 하며, 클라이언트는 정답 여부만 받습니다.

`info`의 `min_dwell_seconds`는 확인 버튼이 활성화되기까지 기다리는 시간입니다.
서버도 스캔 시각과 제출 시각의 차이를 검증합니다.

### v2 — 이후 검토

| 유형 | 이유 |
|---|---|
| ~~`roulette` 룰렛 추첨~~ | **정책 정리 완료 → 경품 뽑기로 구현.** 아래 참고 |
| `receipt` 영수증 인증 | 홍보 활용안(6.5)의 지역 상권 프로모션과 직결되나 OCR·검수 비용이 큼 |
| `ar` AR 포토 | 기기 편차가 커서 야외 축제 현장 검증이 필요 |

**뽑기가 미뤄졌던 이유와 그 해소** — 걸림돌은 "보너스 포인트 산정이 보상 캠페인과
겹친다"였습니다. `participations` 에는 `bonus_points` 와 `reward_campaign_id` 가
각각 하나뿐이라, 뽑기가 포인트를 주면 같은 지급에 캠페인이 겹칠 때 무엇이 이기는지를
스키마가 표현하지 못합니다.

**뽑기를 포인트가 아니라 경품으로 두면 이 충돌이 사라집니다.** 미션 지급 경로를
건드리지 않으므로 참여 이력·포인트 집계·중복 지급 방지가 지금 정의 그대로 남습니다.
그래서 부스 체험 유형(`experience_type`)이 아니라 **조각 보드 완성 보상**으로
구현했습니다 — 계약 §12.

## 4. 참여 흐름

```
부스 QR 스캔
   │
   ▼
GET /scan  ─── 토큰 유효? ──── 아니오 ──▶ "QR을 다시 스캔해 주세요" (410)
   │ 예
   ▼
부스 테마 화면 + 미션 목록 (미션 1개면 바로 다음 단계)
   │
   ▼
체험 진행 (quiz/photo/survey/info/stamp)
   │
   ▼
POST /scan-grants  {booth_id, token, mission_id, response}
   │
   ├── 채점 실패 (quiz 오답) ──▶ 재시도 (max_attempts까지)
   │
   ▼
참여 이력 + 포인트 스냅샷 + 이미지 조각 공개
   │
   ▼
완료 화면: 부스 완료 문구 + 획득 포인트 + 새로 열린 조각
```

**핵심 원칙은 그대로입니다.** 참여자가 스스로 완료를 누를 수 없습니다.
체험을 통과해도 **부스 QR 토큰이 유효해야만** 지급됩니다.
집에서 퀴즈 답을 알아내도 현장에 오지 않으면 완료되지 않습니다.

`staff_scan` 부스는 체험 화면 대신 스태프 확인으로 지급됩니다.
체험 화면은 `participant_scan` 부스에서만 동작하며,
`staff_scan` 부스에 체험을 설정하면 저장 시 그 사실을 안내합니다.

## 5. 재시도와 실패 처리

| 상황 | 처리 |
|---|---|
| 퀴즈 오답 | `max_attempts`까지 재시도. 소진 시 "부스 스태프에게 문의하세요" |
| 사진 업로드 실패 | 참여 이력을 만들지 않고 재시도. 부분 완료 상태를 남기지 않음 |
| 제출 중 토큰 만료 | 재스캔 안내. 이미 입력한 응답은 클라이언트에 유지 |
| 네트워크 끊김 | 응답을 로컬에 임시 보관하고 복구 시 재전송. 중복은 유니크 제약이 흡수 |

시도 횟수는 `participations.attempt_count`에 기록합니다.
완료되지 않은 시도는 참여 이력을 만들지 않으므로 **집계에 섞이지 않습니다.**
운영 대시보드와 사후 리포트의 완료 수는 지금까지의 정의 그대로입니다.

## 6. 사진·설문과 개인정보

사진 업로드와 설문은 개인정보를 다루므로 별도 처리가 필요합니다.
이 부분은 법률 검토가 필요한 영역이며, 아래는 최소 설계 기준입니다.

- 사진 업로드 전 **수집·이용 동의**를 받고, 동의 시각을 기록합니다
- 안내 문구에 수집 목적, 보관 기간, 제3자 제공 여부를 명시합니다
- 사진은 원본 저장소(S3 호환)에 두고 DB에는 URL만 둡니다
- 기본 보관 기간은 **축제 종료 후 90일**이며, 경과분은 배치로 삭제합니다
- 얼굴이 담길 수 있으므로 부스 QR 체험 화면에 촬영 안내를 표시합니다
- 참여자는 자기 사진 삭제를 요청할 수 있어야 합니다
  (`DELETE /participants/me/media/{id}`, secret 인증)
- 설문 응답은 참여 코드와만 연결되며 별도 신원 정보를 수집하지 않습니다

미성년자 참여 비중이 높은 가족형 축제에서는 사진 체험을 기본 비활성으로 두고,
운영자가 명시적으로 켜도록 합니다.

> 실제 서비스 전에 개인정보 처리방침과 동의 문구는 법률 검토를 받아야 합니다.
> 이 문서는 기술 설계 기준일 뿐 법적 검토를 대체하지 않습니다.

## 7. 운영자용 결과 보기

부스별 체험 결과를 운영 대시보드에서 확인합니다.

| 체험 | 보여주는 것 |
|---|---|
| `quiz` | 정답률, 문항별 오답 분포, 평균 시도 횟수 |
| `photo` | 업로드 사진 갤러리 (신고·삭제 가능) |
| `survey` | 문항별 응답 분포 |
| `info` | 평균 체류 시간 |
| `stamp` | 완료 수만 |

설문 결과는 사후 리포트(5.5)의 **정성 지표**로 함께 실립니다.
지금까지 리포트는 완료 수 기반 정량 지표만 있었는데, 설문이 붙으면
"왜 그랬는지"를 처음으로 물어볼 수 있게 됩니다.
단, 응답자는 QR 참여자에 한정되므로 **전체 방문객의 의견이 아니라는 점**을
리포트 문구에 명시합니다. 참여 규모 지표에 붙인 것과 같은 제한입니다.
