# FestaFlow 제품 기획서 (개정판)

지역 축제를 **기획 → 사전 진단 → 현장 운영 → 사후 리포트**까지 하나의 흐름으로 관리하는 웹 서비스.

데이터 구조는 [02-data-model.md](02-data-model.md), API 계약은 [03-api-contract.md](03-api-contract.md)에 있습니다.
설계 판단의 근거는 각 항목 본문에 함께 적혀 있습니다.

## 0. 역할과 화면

| 역할 | 하는 일 | 진입 | 인증 |
|---|---|---|---|
| 기획자 planner | 축제 기획서 작성, 사전 진단, 사후 리포트 열람 | `/planner` | 계정 로그인 |
| 운영관리자 operator | 현장 대시보드, 부스·미션·보드 관리, 보상 캠페인 | `/admin/festivals/{id}/dashboard` | 초대 QR + 6자리 접근 코드 |
| 부스관리자 booth_manager | 현장 확인 후 스탬프 지급, 부스 QR 표시 | `/booth/festivals/{id}` | 초대 QR + 6자리 접근 코드 |
| 참여자 participant | 미션 확인, 이미지 조각 수집 | 현수막·포스터 QR → `/join/{id}` | 익명 코드 + 디바이스 시크릿 |

**QR 4종** — 역할별로 쓰임이 다릅니다.

| QR | 누가 만들고 | 누가 스캔 | 담긴 값 | 유효 |
|---|---|---|---|---|
| 축제 입장 QR | 운영자(포스터·현수막 인쇄) | 참여자 | `/join/{festival_id}` | 영구 |
| 참여자 QR | 참여자 폰 화면 | 부스 스태프 | 참여 코드 `FF-XXXXXXXX` | 영구 |
| 부스 QR | 부스 태블릿 화면 | 참여자 | 부스 ID + 30초 회전 토큰 | 30~60초 |
| 스태프 초대 QR | 운영자 발급 | 스태프 | 축제 ID + 스태프 ID (비밀 아님) | 영구, 코드 필요 |

**시각 규칙** — 저장·연산은 UTC, 표시와 집계 버킷 경계는 `Asia/Seoul` 고정.
구간 집계는 모두 반개구간 `[start, end)`입니다.

## 5. 기획자 기능

### 5.0 기획 파이프라인

기획은 4단계로 진행되며, 각 단계는 앞 단계의 출력을 입력으로 받습니다.

```
STEP 1  기획안 작성          숫자와 목표를 정한다
        /festivals/new       축제명·기간·예상 방문객·예산·예정 프로그램
           │                 └─ 관광 데이터를 보며 수정 (5.3, 5.4)
           ▼
STEP 2  행사 세부 설계        숫자를 공간으로 옮긴다
        /festivals/{id}/layout
           ├─ 내부 지도: 존·부스·시설·인력 배치        → 04
           ├─ 부스별 프로그램과 QR 체험 화면 꾸미기     → 05
           ├─ 동선 설계
           └─ 예산·인력 배치 자동 산출
           ▼
STEP 3  운영·안전 계획        당일 어떻게 굴릴지 정한다
        /festivals/{id}/operations-plan
           ├─ 운영 계획 (시간표·교대·물자)
           ├─ 안전 계획 (위험요소·대응·비상연락)
           └─ 성과 목표 KPI
           ▼
STEP 4  최종 기획서           한 문서로 묶어 본다
        /festivals/{id}/proposal
           └─ 언제든 이전 단계로 돌아가 수정 가능
```

**단계는 순서를 강제하지 않습니다.** 진행 표시일 뿐이며 건너뛰거나 되돌아갈 수 있습니다.
실제 축제 기획은 배치도를 그리다가 예산을 고치고, 안전 계획을 짜다가 부스를 줄이는
왕복 작업이기 때문입니다. `festivals.plan_stage`는 "지금 어디까지 손댔는지"를 기록할 뿐
다음 단계를 잠그지 않습니다.

**사전 진단은 단계가 아니라 상시 도구입니다.** 어느 단계에서든 우측 패널로 열 수 있고,
그 시점까지 입력된 값으로 점수를 계산합니다. 단계가 진행될수록 진단이 쓰는 데이터의
정확도가 올라갑니다.

| 단계 | 진단이 쓰는 수용력 근거 | 진단이 쓰는 프로그램 근거 |
|---|---|---|
| STEP 1 | TourAPI 추정 또는 `venue_capacity` | `planned_*` 예정 프로그램 수 |
| STEP 2 이후 | **배치도 존 수용력 합계 + 동선 병목** | **실제 배치된 부스·미션** |
| STEP 3 이후 | 좌동 | 좌동 + 운영·안전 계획 충족도 |

### 5.1 기획자 워크스페이스 `/planner`

`GET /api/festivals`로 아카이브되지 않은 축제를 생성 시각 내림차순(동률 시 ID 내림차순)으로 조회합니다.
API 요청 중에는 로딩 상태를, 서버 연결 실패 시에는 API 실행 여부 확인 안내를 표시합니다.
축제가 없으면 첫 축제 만들기 안내 화면을 보여줍니다.

**최근 축제 요약 카드** — 가장 최근 생성 축제의 축제명, 기획 상태, 지역, 행사 기간,
사전 진단 점수, 예상 방문객, 기획 예산, 등록된 미션 수와 함께
진단 리포트 · 운영관리자 화면 · 사후 성과 리포트로 가는 링크를 제공합니다.

**축제 목록 카드** — 데모 여부 또는 현재 상태, 축제 ID, 축제명, 지역과 장소, 행사 기간,
예상 방문객, 진단 점수(또는 미진단), 기획 진단 · 부스 운영 바로가기, 보관 버튼.

**축제 보관(구 삭제)** — 확인창에서 다음을 안내합니다.

> 이 축제를 보관합니다. 목록과 집계에서 즉시 사라지며, 참여 이력과 리포트는 30일간 보존됩니다.
> 완전 삭제가 필요하면 운영팀에 요청하세요.

원문의 즉시 물리 삭제를 아카이브로 바꾼 이유는 오조작 한 번에 사후 리포트와 정산 근거가
복구 불가로 사라지기 때문입니다. 실제 물리 삭제는 운영 CLI(`purge_festival`)에서만 수행하며,
아카이브 30일 경과 또는 데모 축제에 한정합니다. 관계 테이블은 `ON DELETE CASCADE`가 걸려 있어
삭제 순서를 애플리케이션이 관리할 필요가 없습니다.

`DEMO_MODE=false`(기본값)이므로 보관한 데모 축제는 서버 재시작 후 복원되지 않습니다.
`true`로 두면 기동 시 데모 축제가 0건일 때만 1건을 시드합니다.

### 5.2 새 축제 생성 `/festivals/new`

단순 기본정보 등록이 아니라 실제 축제 기획서를 작성하는 흐름입니다.
상단 progress로 각 영역을 이동하며, 영역별로 독립된 카드로 표시합니다.

1. 기본 정보 2. 목표와 방문객 3. 예산과 운영 규모
4. 프로그램 구성 계획 5. 교통·혼잡·안전 계획 6. 지역 관광 연계 계획

**필수** — 축제명, 지역, 행사 장소, 시작일, 종료일, 예상 방문객, 총예산.
종료일은 시작일보다 빠를 수 없고(브라우저 · 폼 · API 422 · DB CHECK 4중 차단),
예상 방문객은 0보다 커야 합니다.

**선택 기획 정보** — 한 줄 소개·상세 설명, 개최 목적과 세부 타깃(복수), 핵심 방문 대상,
운영·자원봉사·안전관리 인력, 주차 대수와 동시 수용 인원,
공연·체험·먹거리·지역상점·관광안내·기타 예정 프로그램 수,
대중교통 접근성과 교통·혼잡·안전 대책, 관광지·지역상권·숙박·홍보 연계 계획.
비어 있는 항목은 운영 준비도 진단에서 부족 항목으로 표시됩니다.
숫자 입력에는 명 · 원 · 대 · 개 단위를 함께 표시합니다.

**샘플 기획안 preset** — 아래 3개 중 하나를 선택합니다.
날짜는 버튼을 누른 시점 기준 미래 날짜로 계산하며, 폼에만 채워지고 저장 전 모두 수정 가능합니다.

- 지역 먹거리·문화 축제 — 관광·상권·문화 균형, 18,000명 규모
- 청년 음악·야간 축제 — 20~30대, 공연 중심, 심야 교통·야간 안전 강화
- 가족 체험형 축제 — 8,000명 규모, 체험 중심, 어린이 안전·주차·휴식 강화

**생성 시 자동 처리** — 하나의 트랜잭션에서 다음을 만듭니다.

- `status='planning'`인 축제와 `festival_plans` 행(전부 NULL이어도 생성)
- `status='pending'`인 진단 1건 (외부 API 대기 때문에 비동기 유지)
- 3×3 랜덤 공개 보드 + 타일 9개, 기본 이미지 `/images/chuncheon-stamp-board.png`,
  기본 완료 문구 `모든 축제 조각을 완성했습니다!`
- 생성자를 `operator` 역할 스태프로 등록하고 접근 코드를 1회 노출

생성 후 사전 진단 보기 / 운영안 구성하기를 제시하며,
`DEMO_MODE=true`이면 샘플 부스·미션과 최근 편중 참여를 만든 뒤 대시보드로 이동하는
빠른 테스트를 추가로 제공합니다.

### 5.3 축제 기획 수정 `/festivals/{id}/edit`

`GET /api/festivals/{id}`로 현재 값을 불러와 생성 화면과 **같은 `FestivalFormFields` 컴포넌트**와
같은 검증 규칙으로 수정합니다.

- 저장: `PUT /api/festivals/{id}` → 성공 메시지
- 저장 후 다시 진단: 수정 성공 뒤 `POST /api/festivals/{id}/diagnoses` → 진단 화면 이동
- 로딩 · 저장 중 · 오류 · 성공 상태를 구분하고, 처리 중에는 버튼을 비활성화해 중복 요청을 막습니다

수정은 `updated_at`만 갱신합니다. 진단 이력, 부스, 미션, 참여 기록, 캠페인,
스탬프 보드와 공개 기록에는 손대지 않습니다.

### 5.4 사전 진단 `/festivals/{id}/diagnosis`

축제 기본 정보, 부스·미션 준비도, 관광 데이터를 결합해 100점 만점 준비도를 계산합니다.

**로딩 동작**

1. 축제 기본 정보 조회
2. 최신 완료 진단 조회 (`ORDER BY created_at DESC LIMIT 1`)
3. 관광 인사이트는 병렬 요청
4. 최신 진단이 없거나 `pending`이면 진단을 자동 실행
5. 화면에서 재진단 또는 기획 수정 화면 이동 가능

**재진단은 새 진단 레코드를 추가(append-only)합니다.** 원문처럼 기존 완료 진단을
스냅샷으로 복사하고 최신 진단을 교체하지 않습니다. 각 진단은 계산에 사용한
`input_snapshot`, `rubric_version`, `tourism_snapshot_id`를 함께 저장하므로
나중에도 당시 값 그대로 재현·설명됩니다.

#### 기획 개선 효과

`GET /api/festivals/{id}/diagnoses/comparison`은 최신 완료 진단 2건을 비교합니다.

- 진단이 1건뿐이면 "기획 수정 후 재진단하면 비교할 수 있습니다" 안내
- 총 준비도와 상태의 이전 → 현재 변화
- 5개 항목 전부의 이전 점수, 현재 점수, 증감 (개선·악화·유지 모두 표시, 숨기지 않음)
- 양수 변화 중 가장 큰 항목을 "가장 큰 개선"으로 선정하고,
  그 항목의 현재 `reason`과 `recommendation`을 그대로 노출
- **두 진단의 관광 데이터 공급자가 다르면(실데이터 ↔ 데모 대체) 비교를 표시하지 않고
  사유를 안내합니다.** 외부 API 장애로 인한 점수 변화를 기획 개선 효과로 오해하지 않게 하기 위함입니다

#### 표시 모드 — 점수를 함부로 공개하지 않는다

배점과 계수에는 아직 검증 근거가 없습니다. 그래서 진단은 두 모드로 표시합니다.

| 모드 | 화면에 보이는 것 | 조건 |
|---|---|---|
| `checklist` (기본) | 항목별 **충족 · 부분충족 · 미충족** + 계산 근거 + 개선 제안 | 채점표 미검증 |
| `score` | 100점 만점 점수, 등급, 항목별 점수 막대 | `rubric_calibrations`에 표본 10건 이상 기록이 있을 때 |

점수는 두 모드에서 똑같이 계산되고 저장됩니다. **표시만 감춥니다.**
나중에 백테스트가 끝나면 과거 진단도 소급해서 점수를 볼 수 있습니다.

> **공모전 출품 버전은 `score` 모드로 켭니다.** 지정과제 9번의 핵심 기능이
> "데이터 기반 축제 흥행도 도출"이라, 점수를 감추면 과제 미충족으로 심사에서
> 제외될 위험이 있습니다. 대신 화면에 **"준비도 상대 지표이며 흥행을 보증하지 않는다"** 는
> 문구와 지표별 조회·추정 구분을 항상 함께 표시합니다.
> 상세는 [08-contest-submission.md](08-contest-submission.md) §2.4.1.

근거 없는 78.5점보다 근거 있는 체크리스트가 낫습니다.
"78점인데 망한 축제"가 한 번 나오면 제품 신뢰가 끝나기 때문입니다.
아래 점수 체계는 `score` 모드에서만 노출됩니다.

#### 종합 상태

| 총점 | 위험 수준 | 화면 |
|---|---|---|
| 85점 이상 | stable | 안정 |
| 70~84점 | caution | 주의 |
| 69점 이하 | risk | 위험 |

항목별 수준은 해당 항목 배점 대비 비율로 판단합니다 — 80% 이상 안정,
60% 이상 80% 미만 주의, 60% 미만 위험. 주의·위험 항목의 계산 근거 중 최대 3개를
주요 위험요소로 표시합니다.

#### 진단 산식 (rubric v1)

배점과 구간표는 코드가 아니라 `config/rubrics/v1.json`에 있습니다.
채점표를 바꾸면 새 버전(`v2`)을 추가하며, 과거 진단은 자기가 쓴 버전으로 계속 설명됩니다.

**① 관광수요 적합성 — 25점**
`관광수요 지수 × 0.15 + 계절 적합도 × 10`
관광수요 지수는 체류 강도와 소비 강도의 평균, 계절 적합도는 행사 시작 월과 같은
과거 월의 체류 지수를 0~1로 정규화한 값입니다.

**② 혼잡/수용 안정성 — 30점**
행사 일수(`ends_on - starts_on + 1`)로 예상 방문객을 나눠 일평균 방문객을 구합니다.
일일 수용력은 다음 우선순위로 정하며, 계산 근거에 어느 순위를 썼는지 명시합니다.

| 순위 | 근거 | 계산 |
|---|---|---|
| 1 | **행사장 배치도** (STEP 2 완료 시) | Σ(존 권장 수용 인원) × 하루 2회전 |
| 2 | 기획 입력 `venue_capacity` | 동시 수용 인원 × 하루 2회전 |
| 3 | TourAPI 기반 FestaFlow 추정 | `max(3000, 2500 + √콘텐츠수 × 300)` |

배치도 기준을 쓸 때는 **동선 병목도 함께 반영**합니다.
병목 동선이 하나라도 있으면 혼잡 점수에서 2점, 비상동선 경고가 있으면 3점을 감점하고
그 사실을 계산 근거에 씁니다. 수용 인원은 충분한데 통로가 좁아 사고가 나는 경우를
숫자 하나로는 잡아낼 수 없기 때문입니다.

| 수용력 사용률 | 수용 점수 |
|---|---|
| 75% 이하 | 20점 |
| 75% 초과 90% 이하 | 18점 |
| 90% 초과 100% 이하 | 16점 |
| 100% 초과 115% 이하 | 11점 |
| 115% 초과 | 6점 |

혼잡 점수 = `(1 - 혼잡 위험도) × 10`. 수용 점수와 합쳐 최대 30점.

**③ 프로그램 균형 — 20점**

```
실제 부스가 1개 이상일 때:
  활성 부스 수   × 3점 (최대 8점)
  부스 유형 수   × 3점 (최대 6점)   ← booth_type 코드 기준으로만 집계
  활성 미션 수   × 2점 (최대 6점)

실제 부스가 없을 때:
  planned_* 예정 프로그램 수와 6개 유형 수를 같은 배점 구조로 보조 평가
```

부스가 하나라도 등록되면 planned 값보다 실제 데이터를 우선합니다.
계산 근거에 어느 데이터를 썼는지 표시합니다.
유형 수를 자유 텍스트가 아닌 enum 코드로 세기 때문에,
`food`/`Food`/`푸드`를 따로 입력해 점수를 부풀리는 일이 생기지 않습니다.

**④ 지역 관광 연계성 — 15점**
`인근 관광자원 수 × 1.5` (최대 9점) + `지역 연계 준비도 × 6` (최대 6점)

**⑤ 운영 준비도 — 10점**
설명·핵심 방문 대상·장소·예상 방문객·예산 완성도 최대 4점,
운영 인력·안전 계획·교통 계획·혼잡 대응 계획 최대 4점,
실제 부스와 미션 등록 여부 최대 2점.

#### 진단 결과 화면

종합 준비도 점수와 배지, 주요 위험요소, 5개 항목 점수 막대와 각 항목의 계산 근거·개선 제안,
관광수요·체류·소비·행사 월 적합도 지표, 활용 가능한 지역 관광자원과 이를 근거로 만든 홍보 활용안,
데이터 출처와 기준월, 직전 진단 대비 개선 효과, 가장 큰 개선 항목의 근거와 다음 제안,
입력한 예상 방문객·예산·기간·예정 프로그램·운영 인력·동시 수용·개최 목적 요약.

여기에 **보드 완성 가능성 경고**를 추가합니다.
`타일 수 > 지급 단위 수`이면 "현재 구성으로는 이미지 보드를 완성할 수 없습니다
(9조각 / 활성 부스 5개)"를 진단 화면과 운영 대시보드에 함께 노출합니다.

### 5.5 행사장 설계 (STEP 2) `/festivals/{id}/layout`

기획서의 숫자를 실제 공간으로 옮기는 단계입니다. 상세는 **[04-venue-layout.md](04-venue-layout.md)**.

- 부지 위에 존(무대·먹거리·체험·상점·휴게·운영)을 나누고 부스·시설·인력을 배치
- 주동선·보조동선·비상동선을 그리고 폭 대비 통행량으로 병목을 판정
- 시간 슬라이더로 시간대별 존 밀도 히트맵을 확인
- 기획서 기반 배치 생성으로 `planned_*` 값에서 초안을 자동 생성
- 노드별 예산·필요 인력이 합산되어 **예산 배치표와 시간대별 인력 곡선**이 나옴
- 공간 설계 체크(11개 규칙)와 필수 시설 체크(8종)를 상시 표시

지도에 놓은 `booth` 노드는 실제 `booths` 레코드와 1:1로 연결됩니다.
지도와 부스 목록이 따로 놀지 않고, 운영 대시보드·QR 지급이 같은 데이터를 씁니다.

밀도 계수, 동선 유량, 히트맵은 전부 **FestaFlow 추정 기준**이며 법정 기준이나 실측이 아닙니다.
화면에 그대로 표시합니다.

### 5.6 부스 QR 체험 화면 (STEP 2-b) `/festivals/{id}/booths/{bid}/experience`

부스에 **QR 체험존 사용**을 켜면 참여자 폰에 뜰 화면을 꾸밉니다.
상세는 **[05-booth-experience.md](05-booth-experience.md)**.

부스마다 다루는 체험이 다릅니다.

| 대상 | 정하는 것 |
|---|---|
| 부스 | 생김새 — 커버 이미지, 강조 색, 인사말, 완료 문구 |
| 미션 | 동작 — `stamp` / `quiz` / `photo` / `survey` / `info` |

체험을 통과해도 **부스 QR 토큰이 유효해야만** 지급됩니다.
집에서 퀴즈 답을 알아내도 현장에 오지 않으면 완료되지 않습니다.

**사진 체험은 기본 비활성입니다.** `festivals.allow_photo_experience`가 `false`이면
사진 유형을 아예 고를 수 없습니다. 운영자가 동의 문구와 보관 정책을 확인하고
명시적으로 켜야 열립니다. 얼굴이 담기는 데이터를 기본값으로 수집하지 않기 위해서입니다.
미성년자 비중이 높은 가족형 축제에서는 계속 꺼두기를 권합니다.

**개인 단위 추적은 축제 종료 + 90일에 끝납니다.** 참여 이력의 시각·부스 조합은
사실상 이동 경로 데이터이므로, 그 시점에 참여 코드를 파기하고
`participants.anonymized_at`을 찍습니다. 부스별·시간대별 집계는 개인 식별자가
필요 없는 계산이라 익명화 후에도 사후 리포트가 그대로 동작합니다.

### 5.7 운영·안전 계획 (STEP 3) `/festivals/{id}/operations-plan`

배치도가 나온 뒤 당일 운영 방식을 정하는 단계입니다.
세 개 탭으로 구성합니다.

**운영 계획**

| 항목 | 내용 |
|---|---|
| 시간표 | 프로그램·부스별 운영 시간. 배치도의 노드 운영 시간을 그대로 불러와 편집 |
| 인력 교대 | 배치도가 만든 시간대별 인력 곡선 위에 교대조를 배치 |
| 물자·장비 | 품목, 수량, 담당, 반입·반출 시각 |
| 사전 준비 일정 | D-30 / D-7 / D-1 / D-Day 체크리스트 |

**안전 계획**

| 항목 | 내용 |
|---|---|
| 위험요소 등록 | 위험 내용, 발생 가능성(상·중·하), 영향도(상·중·하), 대응 방안, 담당 |
| 비상 연락망 | 역할, 이름, 연락처, 대체 담당 |
| 대피 계획 | 배치도의 비상동선과 집결지를 연결 |
| 기상 대응 | 우천·폭염·강풍 시 중단 기준과 판단 주체 |

위험요소는 가능성 × 영향도로 위험 등급을 매기고, 등급이 높은 항목에 대응 방안이 비어 있으면
경고합니다. 배치도의 `EMERGENCY_PATH_MISSING` / `SAFETY_STAFF_SHORT` 경고는
이 화면 상단에도 함께 표시합니다. 안전 문제는 설계 화면에만 두면 놓치기 쉽습니다.

**성과 목표 (KPI)**

축제 종료 후 사후 리포트(5.9)가 이 목표와 실제를 나란히 비교합니다.

| 지표 | 기본 제공 | 리포트 대응값 |
|---|---|---|
| 목표 방문객 | `expected_visitors` 자동 연동 | — (측정 불가, 아래 주석 참고) |
| 목표 QR 참여자 | 직접 입력 | 고유 완료 참여자 수 |
| 목표 미션 완료 수 | 직접 입력 | 총 완료 수 |
| 목표 참여자당 완료 | 직접 입력 | 참여자당 평균 완료 |
| 목표 만족도 | 직접 입력 (설문 체험 필요) | 설문 평균 점수 |
| 사용자 정의 지표 | 이름 + 목표값 + 단위 | 수동 입력 |

**목표 방문객은 FestaFlow가 측정할 수 없습니다.** QR 참여자 수는 방문객 수가 아니므로,
이 항목은 리포트에서 자동 달성률을 만들지 않고 참고값으로만 표시합니다.
측정 가능한 목표는 QR 참여 지표와 설문뿐이라는 점을 KPI 입력 화면에서 미리 안내합니다.
측정 못 하는 걸 달성률로 그리는 순간 리포트 전체의 신뢰가 무너집니다.

실측 방문객(`visitor_counts`)이 입력되면 목표 방문객도 달성률을 갖게 됩니다.
그 전까지는 참고값입니다.

### 5.8 최종 기획서 (STEP 4) `/festivals/{id}/proposal`

앞의 모든 단계를 하나의 문서로 묶어 보여줍니다. **읽기 화면이자 편집 진입점**입니다.

문서 구성:

1. 표지 — 축제명, 기간, 장소, 주최, 한 줄 소개
2. 개요 — 개최 목적, 타깃, 핵심 방문 대상, 예상 방문객
3. 사전 진단 요약 — 최신 총점, 5개 항목, 주요 위험요소
4. 행사장 배치도 — 지도 이미지, 존별 요약, 동선 요약
5. 프로그램·부스 목록 — 부스별 프로그램, 체험 유형, 운영 시간
6. 예산 계획 — 총예산, 존별·항목별 배치, 미배정액
7. 인력 계획 — 확보 인력, 시간대별 필요 인력 곡선, 교대표
8. 운영 계획 — 시간표, 물자, 사전 준비 일정
9. 안전 계획 — 위험요소 등록부, 비상 연락망, 대피 계획
10. 성과 목표 — KPI 목록
11. 지역 관광 연계 — 관광자원, 홍보 활용안 (6.5)
12. 데이터 출처 — 관광 데이터 공급자·기준월, 추정치 표기

각 섹션 우측의 **수정** 버튼은 해당 단계 화면의 그 위치로 바로 이동합니다.
최종 기획서라는 이름이지만 잠기지 않습니다. 축제 당일까지 계속 고칠 수 있습니다.

**비어 있는 섹션은 숨기지 않고 "미작성"으로 표시합니다.**
안 쓴 항목이 문서에서 사라지면 빠뜨린 걸 알아채지 못합니다.
상단에 작성 완료율(예: 9/12 섹션)을 함께 보여줍니다.

**내보내기** — PDF와 인쇄용 뷰를 제공합니다.
지자체 보고나 심의 제출에 그대로 쓸 수 있는 형태를 목표로 합니다.
배치도는 벡터로 렌더링해 확대해도 깨지지 않게 합니다.

**버전** — 저장할 때마다 스냅샷을 남기고, 문서 상단에서 이전 버전과 비교할 수 있습니다.
"예산이 언제 어떻게 바뀌었는지"를 추적하는 용도입니다.

### 5.9 축제 사후 성과 리포트 `/festivals/{id}/report`

기획 예상값과 완료 참여 기반 현장 신호를 비교하고 다음 행사 개선안을 제공합니다.

**행사 결과 요약**

- FestaFlow 참여자 — 완료 기록의 고유 참여자 수
- 총 미션 완료 — `status='completed' AND completed_at IS NOT NULL`인 참여 수
- 참여자당 평균 완료 — 총 완료 ÷ 고유 참여자
- 참여 발생 미션 — 완료가 1건 이상 발생한 미션 수와 비율

미션 시도자나 전체 현장 방문객 분모를 알 수 없으므로 임의의 "미션 성공률"은 만들지 않습니다.

**목표(KPI) 대비 실제**

STEP 3에서 입력한 성과 목표와 실제 값을 나란히 놓고 달성률을 표시합니다.
목표를 입력하지 않았으면 이 블록은 생략합니다.

측정 가능한 지표(QR 참여자, 미션 완료, 참여자당 완료, 설문 만족도)만 달성률을 계산합니다.
**목표 방문객은 달성률을 만들지 않고 참고값으로만 표시합니다** — FestaFlow는 방문객을
측정하지 않기 때문입니다. 설문 만족도는 응답자가 QR 참여자에 한정되므로
전체 방문객의 의견이 아니라는 문구를 함께 답니다.

**실측 방문객 기반 참여율**

방문객은 FestaFlow가 측정하지 않지만, **받아올 수는 있습니다.**
운영자가 `visitor_counts`에 일자별 실측치를 출처와 함께 입력하면
리포트가 근거 있는 참여율을 계산합니다.

```
참여율 = 고유 완료 참여자 ÷ 실측 방문객
```

| 출처 | 우선순위 | 표시 |
|---|---|---|
| `beacon` 출입구 센서 | 1 | 그대로 |
| `manual_counter` 입구 계수기 | 2 | 그대로 |
| `partner` 지자체·조직위 집계 | 3 | 출처 명시 |
| `estimate` 주최측 추산 | 4 | **"주최측 추산 기준"** 꼬리표 |

같은 날짜에 여러 출처가 들어오면 우선순위가 높은 하나를 쓰고 나머지는 참고로 병기합니다.
입구 계수기 수치와 지자체 집계가 다른 건 정상이고, 그걸 숨기지 않습니다.

**실측이 하나도 없으면 참여율을 만들지 않습니다.** 아래 참여 규모 지표만 표시합니다.

**계획 vs 실제 참여 신호** (실측이 없을 때)

`예상 대비 FestaFlow 참여 규모 = 고유 완료 참여자 ÷ expected_visitors`

이 값은 QR/미션 서비스의 참여 규모입니다. 예상 방문객이 실제 방문객이었다는 뜻이 아니며,
실제 축제 방문률이나 전체 방문객 대비 참여율로 표현하지 않습니다. API 응답과 화면 문구에도
이 제한을 명시합니다.

**추천 적중률**

`recommendation_feedbacks`가 쌓여 있으면 "운영 추천 N건 중 M건이 현장과 일치(x%)"를
표시합니다. 제품이 자기 추천의 정확도를 스스로 보고하는 항목입니다.

**시간대·부스·미션 성과**

완료 시각을 KST 기준 1시간 단위로 묶은 timeline과 CSS 막대 차트,
부스별 완료 수·고유 참여자·전체 완료 중 비율, 부스별 최다 참여 시간과 완료 수,
완료 수 내림차순 부스 순위(동률은 같은 순위), 미션별 완료 수·고유 참여자·비율.

부스별 집계는 **`participations.booth_id` 스냅샷**을 사용합니다.
운영 중 미션을 다른 부스로 옮겨도 과거 집계가 이동하지 않습니다.
원문은 "현재 미션의 booth_id"로 묶었기 때문에 미션 재배치 한 번에 리포트가 뒤바뀌었습니다.
부스가 보관되어 스냅샷이 해제된 참여는 축제 전체 완료에는 보존하되
특정 부스에 임의 배정하지 않습니다.

**운영 개입 결과와 다음 축제 개선안**

모든 보상 캠페인의 30분 전후 impact를 포함합니다. 데이터 충분·부족 상태,
대상 부스 전후 비율과 %p 변화를 표시하되 인과관계를 단정하지 않습니다.

`services/reports.py`는 설명 가능한 규칙으로 개선안을 생성합니다.

| 조건 | 개선안 |
|---|---|
| 최다 완료 시간대 | 다음 행사 운영인력·대기 동선 강화 검토 |
| 전체 완료 35% 이상 부스 | 공간 확대 또는 인접 분산 검토 |
| 부스 평균 미만 최저 참여 부스 | 위치·프로그램·인센티브 검토 |
| 표본 충분 + 전후 변화 큰 캠페인 | 동일 전략 재검증 검토 |
| 참여 데이터 0건 | 참여 코드 안내와 현장 확인 절차 개선 |

참여 데이터가 없어도 계획 KPI, 명시적 빈 상태, 데이터 수집 개선안을 표시합니다.

## 6. 한국관광공사 데이터 연동

### 6.1 연동 API

한국관광 콘텐츠랩이 공개한 **26종** 전체 목록과 활용 매핑은
[07-tourapi-catalog.md](07-tourapi-catalog.md)에 있습니다.
아래는 현재 연동된 2종이며, 카탈로그 §3의 확장 제안이 반영되면 12종이 됩니다.

| 목적 | 서비스 |
|---|---|
| 지역 체류·소비 수요 강도 | AreaTarDemDsService (지역별 관광 수요 강도) |
| 지역 코드와 관광 콘텐츠 | KorService2 (국문 관광정보 서비스) |

두 키가 모두 있어야 실데이터 공급자를 씁니다.
**실제로는 `KTO_API_KEY` 하나면 됩니다.** 공공데이터포털 인증키는 계정당 하나이고,
승인된 모든 API에 같은 키를 씁니다. 서비스별 키를 따로 받는 구조가 아닙니다.
`KTO_DEMAND_API_KEY` / `KTO_TOUR_API_KEY`는 계정을 분리해 운영할 때를 위한
선택적 오버라이드로만 남겨 둡니다.

포털이 주는 **Encoding / Decoding 두 벌 중 Decoding 키**를 넣고,
호출 시 `quote(unquote(key), safe="")`로 한 번 정규화합니다.
Encoding 키를 그대로 쓰면 HTTP 클라이언트가 재인코딩해 `%2B`가 `%252B`가 되면서
인증이 깨집니다.

### 6.2 지역 코드 결정

춘천은 알려진 TourAPI 지역 코드를 우선 사용하고, 다른 지역은 국문관광정보 `areaCode2`에서
광역·시군구 코드를 검색합니다. 입력 지역명은 영숫자만 남기고
**특별자치도·특별자치시·통합특별시·광역시·특별시** 표현을 제거해 비교합니다.
(`전남광주통합특별시` 같은 개편 명칭이 실제 응답에 나옵니다.)

관광수요 API 코드는 관광 콘텐츠 항목의 **`lDongRegnCd` / `lDongSignguCd`(법정동 코드)** 로
구성합니다. `areacode` / `sigungucode`는 **빈 값인 항목이 매우 많아** 기준으로 쓸 수 없습니다.

해석 결과는 `festivals.area_code / sigungu_code / legal_dong_code`에 **저장**합니다.
원문은 메모리 LRU 캐시만 썼는데, 프로세스 재시작마다 외부 검색이 다시 돌고
결과가 달라질 수 있어 진단 재현성을 해쳤습니다. 메모리 캐시는 그대로 두되
DB 저장값을 1순위로 사용합니다.

### 6.3 관광 지표 생성과 스냅샷

- 체류 강도(코드 21), 소비 강도(코드 22) 조회 → 평균을 관광수요 지수로 사용
- 행사 시작 월과 같은 과거 기준월로 계절 적합도 계산
- 추정 일일 수용력 = `max(3000, 2500 + √콘텐츠수 × 300)`
- 일일 예상 방문객 = `ceil(예상 방문객 ÷ 행사 일수)`
- 혼잡 위험도 — 1순위는 **`DataLabService/tarDecoList`의 관광지별 혼잡도 예측 조회값**입니다.
  해당 지역 데이터가 없으면 `clamp(0.25 + 수요정규값 × 0.35 + 수용초과정규값 × 0.25, 0, 1)`로
  폴백하며, 진단 근거에 조회값인지 추정값인지 명시합니다
- 지역 연계 준비도 = `min(0.95, 0.45 + log1p(콘텐츠수) ÷ 10)`

계산 결과는 `tourism_snapshots`에 **(지역키 + 기준월 + 공급자)** 단위로 저장하고
TTL 7일을 둡니다. 진단은 라이브 호출이 아니라 스냅샷 ID를 참조합니다.
같은 기획을 두 번 진단했을 때 외부 API 변동으로 점수가 흔들리는 문제를 없애기 위함입니다.

**행사장 일일 수용력**만 FestaFlow 추정치로 남습니다.
우리가 그린 배치도에서 계산하는 값이라 공사 데이터에 있을 수가 없습니다.

혼잡 위험도(`tarDecoList`)와 지역 연계 준비도(`TarRlteTarService1`)는
조회값이 있으면 그것을 쓰고, 없을 때만 추정식으로 폴백합니다.
`source_note`와 진단 데이터 출처 문자열에 **지표별로 조회·추정·폴백 여부**를 구분 표시합니다.

### 6.4 지역 관광자원 선택

국문관광정보에서 최대 100개를 조회한 뒤 대표 자원 8개를 고릅니다.
대상 유형은 관광지 · 문화시설 · 여행코스 · 레포츠 · 숙박 · 쇼핑 · 음식점입니다.
유형 판별은 **`lclsSystm1`**(신규 분류체계)을 1순위로 씁니다.
기존 `cat1`은 음식점·쇼핑 계열에서 **빈 값인 항목이 많아** 단독 기준으로 쓰면
해당 자원이 통째로 누락됩니다. `cat1`은 폴백으로만 둡니다.

같은 유형에 몰리지 않도록 유형별 첫 자원을 먼저 뽑고 나머지를 채웁니다.
이미지 URL(`firstimage` / `firstimage2`)은 같은 응답 안에서도 http·https가 섞여 오므로
HTTP면 HTTPS로 바꿉니다. 안 바꾸면 HTTPS 페이지에서 mixed content로 차단됩니다.

`areaBasedList2` 응답만으로 종료일을 판별할 수 없는 축제·행사 콘텐츠 유형은
과거 행사를 추천할 위험이 있어 제외합니다.

### 6.5 홍보 활용안

조회한 실제 자원 이름을 근거로 규칙 기반 아이디어 3개를 만듭니다.

1. 관광지·문화시설·여행코스를 잇는 축제 전후 반나절 코스
2. 음식점·쇼핑 자원과 쿠폰·영수증 인증을 묶는 지역 상권 공동 프로모션
3. 축제의 첫 번째 핵심 방문 대상을 이용한 타깃 맞춤 체험 콘텐츠

각 아이디어에는 제목, 실행 설명, 근거 관광자원 이름, 추천 홍보 채널을 포함합니다.

### 6.6 실패 시 대체 데이터

API 키가 없으면 처음부터 데모 공급자를 사용합니다. 키가 있어도
네트워크·HTTP 오류, JSON 변환 실패, TourAPI 오류 코드, 지역 코드 검색 실패,
관광수요 데이터 없음, 필수 응답값 형식 오류가 발생하면 데모 공급자로 자동 전환합니다.

대체 데이터를 쓰면 화면에 데모 인사이트임을 표시하고,
진단 출처에 `데모 대체 데이터(API 연결 실패)` 문구를 남기며,
스냅샷의 `provider`를 `demo`로 기록합니다. 이 값이 다르면 진단 비교를 표시하지 않습니다(5.4).

## 7. 운영관리자 기능

### 7.1 운영 대시보드 `/admin/festivals/{id}/dashboard`

축제 정보와 스탬프 보드를 병렬 조회하고,
`GET /api/festivals/{id}/operations/insights`로 현장 참여 지표를 별도로 불러옵니다.
지표는 10초 polling + 수동 새로고침을 지원합니다.

polling은 insights 상태만 갱신합니다. 축제·보드 데이터와 부스·미션 편집기 상태를
다시 설정하지 않으므로 작성 중인 폼이나 보드 설정값이 초기화되지 않습니다.
응답에는 `ETag`를 붙이고, 변화가 없으면 `304 Not Modified`를 반환해
축제 당일 폴링 비용을 줄입니다.

**현황 KPI**

| 지표 | 계산 |
|---|---|
| 총 참여자 | 완료 참여의 고유 참여자 수 |
| 총 미션 완료 | `status='completed' AND completed_at IS NOT NULL` 수 |
| 최근 30분 참여 | 조회 시각 기준 `[now-30m, now)` 완료 수 |
| 참여 편중 위험 부스 | 최근 30분 상태가 HIGH인 부스 수 |

**부스 참여 현황** — 완료 참여를 `participations.booth_id` 스냅샷으로 묶어
부스별 누적 완료, 고유 참여자, 최근 10·30·60분 완료, 최근 30분 비율, 마지막 참여 시각을 계산합니다.
가장 활발한/저참여 부스는 최근 30분 완료 기준입니다.

> 이 지표는 GPS·카메라·센서로 측정한 실제 인원수나 물리적 밀집도가 아닙니다.
> 부스에서 검증된 QR/미션 완료 건수를 현장 참여량의 proxy로 쓰는 **참여 편중 위험** 지표입니다.

화면에도 이 제한을 안내하며 실제 혼잡도처럼 표현하지 않습니다.
상태 상수와 판정 함수는 `services/operations_insights.py`에 분리합니다.

| 조건 | 상태 | 화면 |
|---|---|---|
| 최근 30분 축제 전체 완료 10건 미만 | INSUFFICIENT_DATA | 데이터 부족 |
| 충분, 부스 비율 25% 미만 | LOW | 여유 |
| 충분, 25% 이상 40% 미만 | CAUTION | 주의 |
| 충분, 40% 이상 | HIGH | 집중 |

색상뿐 아니라 아이콘·상태 텍스트·판정 이유를 함께 제공합니다.
외부 차트 라이브러리 없이 CSS 막대로 부스별 최근 30분 참여량을 비교합니다.

**FestaFlow 운영 인사이트** — 같은 응답의 `recommendations`에 지금 검토할 행동을 제공합니다.
AI/LLM을 쓰지 않고 `services/operations_recommendations.py`의 상수와 규칙만 사용하며,
HIGH → CAUTION 순으로 반환합니다.

| 유형 | 조건 | 문구 |
|---|---|---|
| REDISTRIBUTE | 활성 부스 하나가 최근 30분 40% 이상이고 다른 활성 부스가 15% 이하 | "지역상점존 QR 완료가 8%입니다. **현장이 실제로 한산한지 확인해 주세요.** 맞다면 한시 추가 보상을 검토할 수 있습니다." |
| NO_ACTIVITY | 최근 30분 전체 20건 이상인데 활성 부스 완료 0건 | "이 부스에서 30분간 완료가 없습니다. **QR이 잘 보이는 자리에 있는지 확인해 주세요.**" |

**추천은 지시가 아니라 확인 요청입니다.** QR 참여자는 방문객의 일부이고,
적극적 참여자에 편향된 표본입니다. 그 데이터로 "이렇게 하세요"라고 지시하면
문구로만 제한을 밝히고 행동은 시키는 구조가 됩니다.

각 카드에 **확인함 / 해당 없음** 버튼을 두어 운영자 판단을 기록합니다.
이 기록은 사후 리포트에서 추천 적중률로 집계되어, 다음 축제에서 로직을 점검하는
근거가 됩니다.

최근 30분 전체 완료가 10건 미만이면 추천을 만들지 않고 빈 배열을 반환하며,
화면은 운영 판단 데이터 부족을 안내합니다. 모든 활성 부스가 균형이면 추천하지 않습니다.
비활성 부스는 집중 출발점과 분산·무참여 대상에서 모두 제외합니다.
카드는 상황 · 판단 근거 · 권장 행동을 구분해 표시하며,
추가 보상 설정 버튼을 누르면 대상 부스가 자동 선택된 캠페인 폼이 열립니다.

### 7.2 추가 보상 캠페인

제목, 참여자 안내 메시지, 보너스 포인트, 시작·종료 시간을 입력해 실행합니다.
대시보드는 현재 활성 캠페인과 종료 시각을 함께 표시합니다.

- `bonus_points >= 0`, `ends_at > starts_at`
- 부스와 선택 미션은 반드시 URL의 축제 소속
- 미션을 지정하지 않으면 선택 부스의 모든 활성 미션에 적용
- 활성 판정 = `is_active AND starts_at <= now() <= ends_at` (서버 시각)
- 같은 미션에 활성 캠페인이 겹치면 **합산하지 않고 최대 보너스 1건만** 적용하며,
  적용된 캠페인 ID를 `participations.reward_campaign_id`에 기록합니다

CRUD와 활성 판정은 `services/reward_campaigns.py`에 있으며 HTTP route에는 검증·지급 계산을 두지 않습니다.
캠페인 생성은 추천 자동 실행이 아니라 운영자의 명시적 제출로만 이루어집니다.

**운영 개입 효과 분석** — 캠페인 시작 시각 기준 30분 window.

```
before: [시작 - 30분, 시작)
after:  [시작, 시작 + 30분)
```

대상 부스의 before·after 완료 수와 증감률, 각 구간 전체 완료 중 비율과 %p 증감,
before에서 대상 부스를 제외하고 40% 이상 집중된 최다 참여 부스가 있으면 그 부스의 집중 비율 변화.
before+after 표본 합계가 20건 미만이면 `INSUFFICIENT_DATA`.

결과는 보상의 인과 효과가 아니라 **캠페인 전후 참여 변화**로 표현합니다.
after 30분이 아직 지나지 않은 활성 캠페인은 집계 중임을 별도 표시합니다.
분석은 `services/reward_campaign_impact.py`에 분리하며 다른 축제 참여는 집계하지 않습니다.

### 7.3~7.6 부스 관리

| 항목 | 규칙 |
|---|---|
| 부스명 | 필수, 2~120자, 축제 내 중복 불가 |
| 유형 | 필수, enum — food / experience / performance / information / local_shop / etc |
| 유형 표시 라벨 | 선택, 최대 60자 |
| 위치 | 선택, 최대 200자 |
| 운영자 | 선택, 최대 120자 |
| 운영 활성 상태 | 기본 활성 |
| 확인 방식 | 필수, `staff_scan`(기본) 또는 `participant_scan` |

**확인 방식** — 부스 성격에 따라 운영자가 고릅니다.

| 방식 | 스캔 방향 | 검증하는 것 | 적합 |
|---|---|---|---|
| `staff_scan` | 스태프가 참여자 QR을 스캔 | 미션 **수행** (사람이 눈으로 확인) | 체험·공연·먹거리 |
| `participant_scan` | 참여자가 부스 QR을 스캔 | 현장 **방문** (그 시각 그 자리에 있었음) | 순회 스탬프, 관광안내, 지역상점 |

`participant_scan`은 스태프 없이도 돌아가 처리량이 높지만, 미션을 실제로 했는지는 확인하지 못합니다.
운영 화면에서 이 차이를 방식 선택 시 그대로 안내합니다.

원문의 자유 텍스트 유형을 enum + 라벨로 바꿨습니다.
진단의 "부스 유형 수 × 3점"이 표기 흔들림으로 부풀지 않게 하기 위함입니다.

**부스와 첫 미션 동시 추가** — 체크 시 미션명, 지급 포인트, 설명, 활성 여부가 펼쳐집니다.
저장은 하나의 트랜잭션에서 부스 세션 추가 → flush로 ID 확보 →
첫 미션 `booth_id`를 새 부스 ID로 **강제 설정** → 함께 커밋합니다.
하나라도 실패하면 전체 롤백이므로 부스만 남는 불완전 상태가 생기지 않고,
클라이언트가 다른 `booth_id`를 보내도 덮어씁니다.

**부스 수정** — 부스명, 유형, 라벨, 위치, 운영자, 활성 상태를 변경합니다.
중지된 부스는 부스관리자 지급 화면 선택 목록에서 제외됩니다.

**부스 삭제(보관)** — 확인창 후 `archived_at`을 설정합니다.
소속 미션은 `booth_id=NULL` 미배정으로 전환하고, 타일 배정을 해제합니다.
공개 이력이 있어도 차단하지 않습니다 — 이력은 `participations.booth_id` 스냅샷과
`stamp_reveals`에 남아 있어 리포트가 깨지지 않기 때문입니다.
원문의 `409` 차단과 "비활성화하세요" 안내는 이 구조에서 불필요해져 제거했습니다.

### 7.7~7.9 미션 관리

| 항목 | 규칙 |
|---|---|
| 미션명 | 필수, 2~120자 |
| 연결 부스 | 선택, 미배정 가능, 같은 축제 소속만(위반 시 400) |
| 지급 포인트 | 0~1,000,000 |
| 설명 | 선택, 최대 2,000자 |
| 참여 가능 상태 | 기본 활성 |

중지된 미션은 부스관리자 지급 화면에서 제외됩니다.
미션 삭제는 `archived_at` 설정이며, 참여 이력의 `mission_id`는 **유지**합니다.
원문은 `mission_id`를 NULL로 바꿨지만, 아카이브 방식에서는 그럴 필요가 없고
"어떤 미션이었는지"를 사후 리포트에서 계속 보여줄 수 있습니다.

지급 시점에 `base_points` / `bonus_points`를 스냅샷으로 저장하므로
미션 수정·보관이나 캠페인 종료 후에도 과거 합계가 변하지 않습니다.

### 7.10 스탬프 이미지 보드 설정

격자는 2×2(4조각) / 2×3(6조각) / 3×3(9조각) 중 선택합니다.

**공개 방식**
- 랜덤 공개 — 아직 열리지 않은 조각 중 하나를 `secrets.choice`로 선택
- 부스 지정 공개 — 타일에 지정된 부스에서 완료한 참여만 해당 타일을 공개
  (한 타일에 한 부스, 한 부스는 한 타일, 격자 범위 밖 인덱스 거부, 타 축제 부스 거부)

**지급 단위 (신규)**
- `booth` — 부스당 1조각. 부스 순회를 유도합니다
- `mission` — 미션 완료마다 1조각

원문은 부스당 1조각으로 고정되어 있어, 3×3 보드(9조각)에 부스가 5개면
어떤 참여자도 보드를 완성할 수 없는데 그 사실을 아무도 알 수 없었습니다.
지급 단위를 선택 가능하게 하고, `타일 수 > 지급 단위 수`이면
대시보드와 진단 화면에 완성 불가 경고를 상시 노출합니다.
저장 자체는 막지 않습니다 — 준비 단계에는 부스가 아직 없을 수 있기 때문입니다.

**설정 저장 (변경됨)**
격자 · 공개 방식 · 지급 단위 중 하나라도 바뀌면 보드 `version`을 올리고 새 타일 집합을 만듭니다.
기존 공개 이력은 **삭제하지 않고** 이전 버전 기록으로 보존합니다.
공개 이력이 1건이라도 있으면 API가 `409 requires_confirmation`을 반환하고,
UI는 "참여자 N명의 진행이 초기화됩니다"를 경고한 뒤 재확인을 받습니다.
원문은 경고 없이 즉시 삭제했기 때문에, 축제 당일 오조작 한 번으로
모든 참여자의 수집 진행이 복구 불가로 사라졌습니다.

`image_url`과 `complete_message`만 바꾸는 것은 버전 변경이 아니며 진행이 유지됩니다.
두 값의 편집 UI를 이번 범위에 포함합니다(원문에서는 미구현 상태였습니다).

## 8. 부스관리자 기능

### 8.1 부스 지급 화면 `/booth/festivals/{id}`

참여자가 스스로 완료를 누를 수 없다는 원칙은 두 방식 모두에서 유지됩니다.
`staff_scan`은 사람이, `participant_scan`은 30초마다 바뀌는 부스 QR이 현장 확인을 대신합니다.

**로그인** — 운영자가 발급한 초대 QR을 스캔하면 로그인 화면이 열리고,
6자리 접근 코드를 입력해야 세션이 발급됩니다. QR만으로는 들어갈 수 없으므로
QR 사진이 유출돼도 지급 권한이 새지 않습니다.
`booth_manager` 토큰은 배정된 부스만 조작할 수 있습니다(위반 시 403).

**부스 선택** — 활성 부스만 표시하고 첫 부스를 기본 선택합니다.
부스 유형, 이름, 위치, 담당 운영자를 보여주고, 부스를 바꾸면 이전 지급 결과와 메시지를 초기화합니다.
`booth_manager` 토큰은 배정된 부스 1개만 보이므로 선택 UI가 나타나지 않습니다.

화면은 선택 부스의 `verify_mode`에 따라 두 모드로 갈립니다.

#### staff_scan — 스태프가 참여자 QR을 스캔

**스캐너** — 브라우저 카메라(`getUserMedia` + `BarcodeDetector`, 미지원 시 JS 폴백)로
참여자 폰의 QR을 읽어 참여 코드를 채웁니다. 조명·카메라 문제를 대비해
**수동 입력 폴백**을 항상 함께 둡니다. 코드는 공백 제거 후 대문자로 정규화하며
(클라이언트·서버 양쪽) 4~80자만 허용합니다.

**미션 표시** — 선택 부스에 연결된 활성 미션만, 제목 · 설명 · 지급 포인트 · 지급 버튼과 함께 표시합니다.
스태프가 미션 수행을 눈으로 확인한 뒤 지급을 누릅니다.

#### participant_scan — 부스 QR을 참여자가 스캔

부스가 QR을 어떻게 내놓는지는 `booths.qr_mode`로 정합니다.
**인쇄가 기본값**입니다. 보안을 이유로 장비를 강요하면 그 기능은 안 쓰이고,
안 쓰이는 보안은 보안이 아닙니다.

| 모드 | 필요 장비 | 토큰 | 약점과 보완 |
|---|---|---|---|
| `printed` (기본) | 인쇄물 한 장 | 부스 고정 서명 | QR 사진으로 원격 완료 가능 → **스태프 확인 병행** 또는 이상 패턴 탐지 |
| `rotating` (상위) | 태블릿·전원·네트워크 | 5분 회전 HMAC | 거의 없음 |

지역 축제 천막 부스에 태블릿과 상시 전원이 없는 경우가 대부분이라,
회전 QR은 장비가 있는 부스가 켜는 상위 옵션으로 둡니다.

**인쇄 QR** — `/join/{festival_id}/scan?b={booth_id}&s={signature}`.
`signature`는 부스 비밀키로 만든 고정 서명이라 재발행 전까지 유효합니다.
운영자 화면에서 부스별 QR 인쇄용 PDF를 내려받습니다.

**회전 QR** — 부스 태블릿을 전체화면 표시 모드로 두면
`GET /festivals/{id}/booths/{bid}/scan-token`을 30초마다 호출해 QR을 갱신합니다.
토큰 유효 window는 **5분**이며 서버는 현재와 직전 window를 인정합니다.
화면에는 부스명, QR, 남은 시간 게이지, 오늘 지급 수를 함께 표시합니다.

원래 30초였던 window를 5분으로 늘린 이유는 오프라인 대응 때문입니다.
통신이 끊긴 상태에서는 서버가 토큰을 검증할 수 없어,
스태프 단말이 서명만 로컬로 확인하고 window 검사는 동기화 시점에 서버가 수행합니다.
30초 window로는 이 지연을 감당할 수 없습니다.

**네트워크 끊김** — 토큰 갱신이 실패하면 QR을 흐리게 처리하고
"연결 확인 중" 배지를 띄웁니다. 만료된 QR을 계속 보여주면
참여자가 스캔하고도 실패하는 상황이 반복되기 때문입니다.
복구되지 않으면 스태프가 임시로 `staff_scan`이나 `printed`로 전환할 수 있습니다.

#### 오프라인 우선 지급

축제장 통신은 끊기는 게 기본값입니다. 수천 명이 모인 야외에서
LTE가 버티지 못하는 건 예외 상황이 아닙니다. **지급 경로만큼은 오프라인에서 완결**됩니다.

1. 스태프 화면이 부스·미션·활성 캠페인 정보를 미리 받아 로컬에 캐시합니다
2. 통신이 끊겨도 지급 버튼이 동작하고, 요청은 **로컬 큐**에 쌓입니다
3. 각 요청에는 클라이언트가 만든 `client_request_id`(UUID)가 붙습니다
4. 복구되면 큐를 순서대로 전송합니다. 재전송이 일어나도
   `UNIQUE (client_request_id)` 제약이 중복 지급을 막습니다
5. 서버는 `queued_at`(현장에서 누른 시각)과 `synced_at`(도달 시각)을 따로 기록합니다.
   **집계는 `completed_at` 기준이며, 이 값은 `queued_at`을 씁니다** —
   그래야 통신 복구 시각에 완료가 몰려 보이는 왜곡이 생기지 않습니다

화면에는 큐에 몇 건이 남았는지, 마지막 동기화가 언제였는지를 항상 표시합니다.
"보낸 줄 알았는데 안 갔다"가 현장에서 제일 위험합니다.

**참여자 화면도 마지막 보드 상태를 로컬에 캐시**합니다.
통신이 없어도 지금까지 모은 조각은 볼 수 있습니다.

운영 대시보드와 인사이트는 오프라인 대응 대상이 아닙니다.
그건 못 봐도 축제는 굴러가지만, 지급이 막히면 참여자가 부스 앞에 멈춰 섭니다.

#### 지급 검증

두 모드 모두 같은 서비스 함수를 타며, 앞단의 **현장 확인 근거만** 다릅니다.

| 순서 | staff_scan | participant_scan |
|---|---|---|
| 1 | 스태프 토큰이 이 축제·부스 권한을 갖는지 | 참여자 secret이 유효한지 |
| 2 | — | 부스 QR 토큰이 현재 또는 직전 window와 일치하는지 |
| 3 | 부스가 해당 축제 소속이고 활성인지 | 좌동 |
| 4 | 미션이 해당 축제 소속·해당 부스 연결·활성인지 | 좌동 |
| 5 | — | 같은 부스·window·참여자로 이미 지급했는지 |
| 6 | 참여 이력 생성 또는 기존 조회 | 좌동 |
| 7 | 완료 상태·시각·포인트 스냅샷·부스 스냅샷·`verified_via` 기록 | 좌동 |
| 8 | 이미지 조각 공개 | 좌동 |

다른 부스의 미션을 지급하려 하면 `409`로 차단합니다.
만료된 QR 토큰은 `410 SCAN_TOKEN_EXPIRED`로 응답하고, 참여자 화면은
"부스 화면의 QR을 다시 스캔해 주세요"를 안내합니다.

**1 스캔 = 1 미션** — `participant_scan`에서 같은 window로 두 번째 미션을 지급하려 하면
거부합니다. 부스 QR은 방문을 확인할 뿐 개별 미션 수행을 확인하지 못하므로,
한 번 스캔으로 그 부스 미션을 전부 쓸어담는 것을 막습니다.
(`booth_scan_uses`의 `UNIQUE (booth_id, window_index, participant_id)`)

**중복 지급 방지** — `UNIQUE (participant_id, mission_id)` 부분 인덱스로 DB가 보장합니다.
서버는 `INSERT ... ON CONFLICT DO NOTHING` 후 기존 행을 반환하며 `was_already_granted=true`를 표시합니다.
조각 공개도 `(board_id, board_version, participant_id, booth_id)` 유니크 제약으로
부스당 1조각을 보장합니다. 원문은 이 규칙이 애플리케이션 코드에만 있어
현장 더블클릭·동시 요청에서 중복 행이 생길 수 있었습니다.

**트랜잭션 일관성** — 참여 완료를 세션에 반영한 뒤 조각 공개를 처리합니다.
조각 공개가 실패하면 참여 완료까지 롤백되어, 미션만 완료되고 조각은 없는 상태를 막습니다.

**최근 지급** — 현재 부스의 완료 참여를 최신순 8건까지 참여자 코드, 미션명, 지급 시각으로 표시하며
새로고침 버튼을 제공합니다.

## 9. 참여자 기능

### 9.1 참여 화면 `/join/{id}`

**진입** — 현수막·포스터·리플릿에 인쇄된 축제 QR을 폰 기본 카메라로 찍으면 바로 열립니다.
앱 설치나 회원가입이 없고, 첫 화면에서 참여 코드가 즉시 발급됩니다.
축제 QR은 `/join/{festival_id}` 하나뿐이라 인쇄물을 부스별로 나눠 만들 필요가 없습니다.

**참여 코드 발급 (변경됨)**
처음 방문하면 `POST /api/festivals/{id}/participants`를 호출합니다.
서버가 `FF-XXXXXXXX` 형식 코드를 발급하며 축제 내 유일성을 보장하고,
함께 내려주는 `participant_secret`을 브라우저에 저장합니다.

```
localStorage: festaflow-participant-{festivalId} = { code, secret }
```

같은 브라우저로 다시 접속하면 저장된 값을 재사용합니다.

**기기 변경 복구** — 3일 축제 이틀차에 폰을 바꾸거나 브라우저 데이터를 지우면
모은 조각이 전부 날아갑니다. 그래서 발급 화면에서 **휴대폰 뒷 4자리를 선택 입력**받습니다.

- 새 기기에서 `참여 코드 + 뒷 4자리`를 입력하면 secret을 재발급합니다
- 축제별 솔트와 함께 **해시만** 저장하며 원문은 남기지 않습니다
- 복구 시도는 코드당 **5회**로 제한합니다 (뒷 4자리는 1만 분의 1이라 무제한이면 뚫립니다)
- 축제 종료 후 해시는 즉시 폐기합니다
- 입력하지 않아도 참여는 가능하며, **그 경우 복구가 안 된다는 것을 그 자리에서 안내**합니다

전화번호 전체를 받지 않습니다. 받는 순간 개인정보 수집 범위가 완전히 달라집니다.

복구를 쓰지 않으면 다른 브라우저·시크릿 모드·다른 기기는 별도 참여자로 인식됩니다.

코드는 부스에서 육안·구두로 노출되는 값이므로, **조회 계열 API는 secret으로 인증**합니다.
코드만 아는 사람은 남의 보드를 열람할 수 없습니다.
부스 지급은 코드만으로 가능해 현장 운영성은 그대로입니다.
원문은 코드 하나로 조회와 지급이 모두 가능해, 옆에서 코드를 본 사람이
남의 수집 현황을 그대로 들여다볼 수 있었습니다.

**내 QR** — 참여 코드를 화면 상단에 **QR로 크게** 표시합니다.
`staff_scan` 부스에서는 이 QR을 스태프에게 보여주면 됩니다.
QR 아래에 코드 문자열과 복사 버튼을 함께 두어, 카메라가 안 될 때 구두·수동 입력으로 폴백합니다.
QR 렌더링은 클라이언트에서 처리하며 외부 이미지 서버를 거치지 않습니다
(참여 코드가 제3자 서버 로그에 남지 않게 하기 위함입니다).

**부스 QR 스캔** — 화면의 "부스 QR 스캔" 버튼을 누르면 카메라가 열립니다.
`participant_scan` 부스의 태블릿 QR을 찍으면 `/join/{id}/scan?b={booth_id}&t={token}`으로 이동합니다.
스캔 화면은 그 부스의 활성 미션을 보여주고, 하나를 선택하면 지급이 완료됩니다.

- 토큰이 만료됐으면(30~60초 초과) "QR을 다시 스캔해 주세요"를 안내합니다
- 같은 window에서 이미 지급받았으면 "이 부스에서 방금 스탬프를 받았습니다"를 안내합니다
- 폰 기본 카메라 앱으로 찍어도 같은 URL이 열리므로, 앱 내 스캐너는 편의 기능입니다

**자동 동기화** — 축제 정보, 개인 스탬프 보드, 활성 보상 캠페인을 3초마다 다시 조회합니다.
공개 조각 수가 늘면 3.5초 동안 새 조각 강조 메시지를 표시합니다.

**포인트 계산** — 지급 시점에 기본 미션 포인트와 당시 활성 캠페인 보너스를 각각
`base_points` / `bonus_points`로 저장하고, 합계는 DB 생성 컬럼이 계산합니다.
캠페인 종료·비활성화나 이후 미션 포인트 수정이 과거 지급액을 바꾸지 않습니다.
같은 미션을 다시 지급해도 기존 이력과 지급액을 그대로 반환하므로 보너스가 중복 적용되지 않습니다.

포인트 전용 원장 테이블은 아직 없지만, 완료 1건당 실제 지급액을 기본/보너스로 분리 고정하여
현재 구조에서 필요한 이력 일관성과 캠페인 추적성을 모두 확보합니다.

**실시간 보너스 안내** — 활성 캠페인이 있으면 상단에 선물 아이콘, 제목·메시지, 대상 부스,
추가 포인트와 남은 시간을 표시합니다. `GET /api/festivals/{id}/reward-campaigns?active_only=true`의
**서버 시각 판정 결과만** 노출합니다.

**미션 목록** — 미션명, 연결 부스(또는 축제 공통 미션), 설명, 포인트,
부스 확인 대기 / 지급 완료 상태를 표시합니다.
참여자가 직접 완료할 수 있는 버튼이나 공개 API는 제공하지 않습니다.

활성 미션만 표시하되, **이미 완료한 미션은 비활성이어도 완료 상태로 계속 표시**합니다.
원문은 비활성 미션까지 모두 보여줘, 참여자가 중지된 미션을 들고 부스에 갔다가 거절당했습니다.

**부스 안내** — 활성 부스의 이름, 유형, 위치를 표시합니다.

### 9.2 이미지 보드 `/join/{id}/stamp-board`

저장된 참여 코드와 secret이 있어야 조회합니다. 없으면 참여 화면에서 시작하도록 안내합니다.

축제명, 공개 조각 수와 전체 조각 수, 격자 크기, 잠긴/공개된 타일, 남은 조각 수,
완성 시 운영관리자가 설정한 완료 문구, 랜덤 또는 부스 지정 컬렉션 표시.

공개된 타일은 하나의 원본 이미지를 CSS `background-position`과 `background-size`로 나눠 보여줍니다.
모든 타일이 열리면 전체 그림이 완성됩니다.

보드 버전이 올라간 경우, 이전 버전에서 모은 조각은 현재 보드 진행에 반영되지 않지만
"이전 보드에서 N조각을 모았습니다" 안내로 기록을 보여줍니다.

## 10. 스탬프 공개 내부 규칙

이미지 공개는 참여자별로 독립적입니다.

**공개 전 조건**
1. 해당 축제의 이미지 보드 존재
2. 활성 부스 존재
3. 참여자가 해당 부스 미션을 완료한 이력 존재
4. `grant_unit='booth'`이면 같은 부스에서 이미 공개한 기록이 없을 것
5. 현재 보드 버전에서 공개 가능한 타일 존재

**랜덤 방식** — 현재 참여자에게 아직 공개되지 않은 타일 중 하나를 `secrets.choice`로 선택합니다.

**부스 지정 방식** — 아직 공개되지 않았고 `assigned_booth_id`가 현재 부스인 타일만 후보입니다.
후보가 없으면 공개하지 않고 오류로 처리합니다.
이 경우 부스관리자 화면에는 "이 부스에 배정된 조각을 이미 받았습니다"처럼
참여자에게 설명 가능한 문구를 표시합니다.

**개인별 직렬화** — 같은 보드라도 참여자에 따라 각 타일의
`is_revealed`, `revealed_by_booth_id`, `revealed_at`과 보드의 `revealed_count`, `is_complete`가 달라집니다.
인증 없이 보드를 조회하면 공개 조각이 없는 기본 보드 상태로 직렬화됩니다.
