# 02 — 제품 범위와 기능

전략 문서(`01-strategy.md`)의 North Star는 **분기당 결과보고서를 내보낸 축제 수**입니다.
아래 모든 기능은 그 숫자에 어떻게 기여하는지로 판단합니다.

> **범위는 줄이지 않습니다.** 여기의 MVP는 기능을 잘라내는 경계가 아니라
> **첫 릴리즈 관문**입니다. v1 항목도 전부 만들며, 다만 첫 축제를 실제로 굴려 보기 전에는
> 뒷단 기능을 확정하지 않습니다.

## 1. 사용자 여정

**대행사 담당자 (1차 세그먼트)**

```
진입     지자체 용역 수주 → 축제 기획서를 써야 함 → FestaFlow에 축제 등록
  ↓
설계     기본 정보와 예산 입력 → 관광 데이터로 예상 방문객·수용력 점검
         → 행사장 배치와 동선 그리기 → 예산·인력 배치 확인
  ↓
준비     부스와 미션 등록 → 부스마다 QR 체험 화면 꾸미기
         → 스태프 접근 코드 발급 → QR 인쇄물 출력
  ↓
당일     부스 스태프가 QR로 스탬프 지급 (통신 끊겨도 로컬 큐)
         담당자는 대시보드에서 참여 편중 확인 → 필요 시 보상 캠페인
  ↓
마감     실측 방문객 입력 → 결과보고서 자동 생성 → PDF로 지자체 제출
  ↓
반복     다음 축제 등록 시 지난 축제 데이터가 기획의 출발점이 됨
```

**관객 (사용자이지만 구매자가 아님)**

```
현수막 QR 스캔 → 참여 코드 즉시 발급(설치·가입 없음)
  → 부스 방문 → 스탬프 → 조각 열림 → 내 지도가 채워짐
  → 9조각 완성 → 공유 카드
```

## 2. 기능 목록

| ID | 기능 | 해결하는 문제 | 사용자 가치 | 크기 |
|---|---|---|---|---|
| F-1 | 축제 기획 기록 | 기획서가 한글 파일에 갇혀 재사용 불가 | 기획 데이터가 구조화되어 뒷단 전부의 입력이 됨 | M |
| F-2 | 사전 진단 (관광 데이터 연동) | 예상 방문객 근거가 "작년에 그랬으니까" | 수용력·계절·지역 연계를 근거로 점검 | L |
| F-3 | 행사장 설계 (지도·동선) | 배치가 머릿속과 손그림에만 있음 | 배치에서 예산·인력·병목이 자동 산출 | L |
| F-4 | 부스·미션 관리 | 부스 목록이 엑셀에 흩어짐 | 현장 운영과 집계가 같은 데이터를 씀 | M |
| F-5 | 부스 QR 체험 화면 | 스탬프가 다 똑같아 지루함 | 부스마다 다른 퀴즈·안내·설문 | M |
| F-6 | QR 스탬프 지급 (오프라인 우선) | 종이 스탬프는 데이터가 안 남고 위조됨 | 통신이 끊겨도 지급되고 나중에 동기화 | L |
| F-7 | 이미지 조각 보드 | 스탬프를 다 모을 동기가 약함 | 그림 한 장을 완성하는 수집 구조 | M |
| F-8 | 관객 참여 화면 (내 지도) | 관객이 어디를 안 가봤는지 모름 | 안 가본 존이 흐리게 보여 순회를 유도 | M |
| F-9 | 운영 대시보드 | 어느 부스에 몰리는지 현장 사람 머릿속에만 | 참여 편중을 실시간에 가깝게 확인 | L |
| F-10 | 보상 캠페인 + 전후 분석 | 편중을 알아도 손쓸 수단이 없음 | 한시 보너스로 분산 유도, 전후 변화 기록 | M |
| F-11 | 운영·안전 계획 + KPI | 안전 계획이 문서로만 존재 | 배치도와 연결된 위험요소·교대·목표 | M |
| F-12 | 최종 기획서 + PDF | 산출물을 다시 한글로 옮겨 적어야 함 | 제출 가능한 문서로 바로 내보내기 | M |
| F-13 | 사후 결과보고서 | 보고서에 쓸 근거가 사진뿐 | 참여·시간대·부스·KPI가 자동 집계 | L |
| F-14 | 실측 방문객 입력 | 우리는 방문객을 못 셈 | 남이 센 숫자를 받아 참여율을 계산 | S |
| F-15 | 스태프 접근 제어 | URL만 알면 누구나 포인트 지급 | 역할·부스 단위 권한 | M |
| F-16 | 기관·요금제 | 여러 기관 데이터가 섞임 | 테넌트 분리와 과금 근거 | M |

## 3. 우선순위

범위는 **두 갈래**로 나눕니다. 목적이 다르고 마감이 다릅니다.

```
Track B — 공모전 출품    🚨 마감 2026.09.21(월) 16:00 — 최우선
  1차 심사 배점 100점 중 구현성 30점이 통째로 비어 있음.

Track A — 11월 학교축제 파일럿 (11/3~11/7)   목적: 가정 ② 검증
  공모전 제출 이후. 최종 심사(10/28) 발표에 "실증 예정"으로 활용.
```

**순서는 B → A입니다.** 학교축제가 공모전 제출 마감보다 6주 늦기 때문에
파일럿 데이터를 출품작에 넣을 수 없습니다.
단 최종 심사가 10/28이라, 진출하면 **"11/3~7 한림대 SW Week 적용 확정"** 을
실용성 근거(25점)로 발표할 수 있습니다.

**둘을 한 덩어리로 만들면 둘 다 늦습니다.** 학교축제에 TourAPI 진단은 의미가 없고
(캠퍼스에 지역 관광수요를 진단할 이유가 없습니다), 공모전 심사에 오프라인 큐는
보이지 않습니다. 자세한 제출 요건과 5주 역산 일정은
**[08-contest-submission.md](../08-contest-submission.md)** 를 보세요.

### Track A — 11월 파일럿 (관문)

| # | 기능 | 범위 | 크기 |
|---|---|---|---|
| 1 | **축제·부스·미션 등록** | F-1 축소 + F-4. 기획 상세 필드 없이 이름·기간·장소만 | S |
| 2 | **스태프 접근 코드** | F-15 그대로. 없으면 아무나 지급 가능 | M |
| 3 | **QR 스탬프 지급** | F-6에서 **오프라인 큐 제외**. 온라인 전용 | M |
| 4 | **조각 보드 + 관객 화면** | F-7 + F-8. **핵심 가설이 여기 있음** | M |
| 5 | **파일럿 리포트** | F-13 축소. 참여자·완료·시간대·부스별만 | M |

**L 사이즈가 하나도 없습니다.** 이전 관문은 L 3개라 3~4개월짜리였는데,
11월까지 3개월이고 그 안에 현장 리허설까지 해야 합니다.

### Track A에서 뺀 것과 근거

| 뺀 것 | 근거 |
|---|---|
| **오프라인 큐** (IndexedDB + SW) | 캠퍼스는 와이파이가 깔려 있습니다. 통신 두절 리스크가 지역 축제보다 훨씬 낮고, SW 디버깅에 쓸 시간이 없습니다. **파일럿에서 실제로 끊기는지 측정**하고 그 데이터로 판단합니다 |
| **운영 대시보드 실시간 인사이트** (F-9) | 부스 10~20개 규모에서 "참여 편중 분석"은 의미가 없습니다. 눈으로 보이는 규모입니다. **단순 현황판**(총 참여자·완료 수·부스별 카운트)으로 대체 |
| **보상 캠페인** (F-10) | 편중 분석이 없으면 쓸 계기가 없습니다 |
| **행사장 설계** (F-3) | 학교축제에 배치도 에디터는 과잉입니다 |
| **부스 QR 체험** (F-5) | 기본 스탬프로 **참여가 발생하는지 먼저** 확인. 체험 유형은 그다음 |
| **최종 기획서** (F-12) | 학생회는 지자체 제출 문서가 없습니다 |
| **멀티테넌시 UI** (F-16) | 축제 1건이면 불필요. 단 **`organization_id` 컬럼은 스키마에 넣어둡니다** — 나중에 소급하면 데이터 유출 위험이 있다고 이미 결정했습니다. 컬럼만 넣고 화면은 안 만듭니다 |

### Track B — 공모전 출품

| 기능 | 상태 |
|---|---|
| **F-2 사전 진단 + TourAPI 연동** | 관광 데이터 활용도가 심사 요소. **12종 API 활용**(`docs/07-tourapi-catalog.md`) |
| F-14 실측 방문객 | `DataLabService` 방문자수 연동 |
| 데모 축제 시연 | 춘천 등 실제 지역 축제 데이터로 진단 결과 시연 |

Track B는 **학교축제 일정과 독립**입니다. 파일럿이 밀려도 출품에 영향이 없고,
반대도 마찬가지입니다.

> **파일럿 결과를 출품작에 넣을 수 있다면 최고의 시나리오입니다.**
> 실증 데이터가 있는 공모전 출품작은 드뭅니다.
> 제출 마감이 11월 이후라면 Track A 결과를 반드시 포함하세요.

### v1 — 파일럿 이후 (12월~)

파일럿 측정 결과에 따라 우선순위가 바뀝니다.

| 측정 결과 | 다음에 만들 것 |
|---|---|
| 참여율 3% 이상, 완성률 높음 | F-5 체험 유형 · F-9 편중 인사이트 · F-10 캠페인 — 규모를 키움 |
| 참여율 낮음 (1% 미만) | **기능 추가 중단.** 참여 구조 자체를 재설계 |
| 통신 끊김 다발 | F-6 오프라인 큐를 최우선으로 승격 |
| 지급 병목 발생 | `participant_scan` 모드(부스 QR)를 우선 구현 |

그 외: F-3 행사장 설계 · F-11 운영·안전 계획 · F-12 최종 기획서 · F-16 멀티테넌시 UI

### Later

축제 간 비교 리포트 · 진단 점수 공개(백테스트 후) · QR 인쇄물 제작 대행

## 3.1 로드맵 — 11월에서 역산

```
8월 하순   ★ 학교축제 주최 측 컨택          ← 코드보다 이게 먼저
           스키마 + packages/shared 확정 (BE-0)
           ① 부스 몇 개인지 ② 예상 인원 ③ 와이파이 되는지 ④ 스태프 몇 명인지

9월        Track A 구현 (관문 5개)
           주차별: 1주 등록·인증 / 2주 지급·보드 / 3주 관객화면 / 4주 리포트

10월 초    기능 동결. 현장 테스트
           ★ 실제 캠퍼스에서 부스 3개 세팅해 리허설
           통신 상태·QR 인식률·직사광선 가독성 측정

10월 중순  리허설 피드백 반영. 스태프 교육 자료
           QR 인쇄물 출력, 접근 코드 발급

11월       ★ 축제 당일 — 5개 지표 측정
           직후 리포트 생성, 주최 측 피드백 수집

병행       Track B (공모전) — TourAPI 진단, 데모 축제 시연
           병행 — 대행사 인터뷰 5건 (가정 ①③ 검증)
```

**8월 하순의 컨택이 가장 중요합니다.** 11월 축제면 준비위가 이미 꾸려졌고,
9월이면 부스 모집이 시작됩니다. 그 전에 들어가야 부스 명단을 받고
QR 인쇄물을 준비 일정에 끼워 넣을 수 있습니다. **늦으면 파일럿 자체가 무산됩니다.**

## 4. 의존관계

```
F-16 기관·요금제
   └→ F-1 축제 기획 기록
         ├→ F-2 사전 진단 ──────────────┐
         ├→ F-3 행사장 설계 ────────────┤
         │     └→ F-11 운영·안전 계획 ──┤
         └→ F-4 부스·미션 관리          │
               ├→ F-5 부스 QR 체험      │
               ├→ F-15 스태프 접근 제어 │
               │     └→ F-6 QR 스탬프 지급
               │           ├→ F-7 이미지 조각 보드
               │           │     └→ F-8 관객 참여 화면
               │           └→ F-9 운영 대시보드
               │                 └→ F-10 보상 캠페인
               └────────────────────────┴→ F-12 최종 기획서
                                            F-13 사후 결과보고서
                                               ↑
                                            F-14 실측 방문객
```

**F-3 → F-2** 는 단방향 강화 관계입니다. 배치도가 있으면 진단의 수용력 근거가
`venue_capacity` 숫자 하나에서 존 면적 합계로 올라갑니다. 배치도 없이도 진단은 동작합니다.

**F-14 → F-13** 도 선택적입니다. 실측 방문객이 없으면 참여율을 만들지 않고
참여 규모만 보고합니다.

## 5. 열린 질문

사람이 답해야 하는 결정입니다. 개발로 풀 수 없습니다.

### 지금 당장 (8월 안에)

**0-a. 학교축제 주최 측을 언제 만나는가?**
부스 수·예상 인원·와이파이 여부·스태프 인원을 모르면 Track A의 범위를 확정할 수 없습니다.
부스가 5개면 3×3 보드는 완성 불가이고(타일 9개 > 부스 5개),
스태프가 부족하면 `participant_scan`(부스 QR) 모드가 필요합니다.
**이 답이 관문 설계를 바꿉니다.**

**0-b. 공모전 제출 마감이 언제인가?**
11월 이후면 파일럿 실증 데이터를 출품작에 넣을 수 있습니다.
11월 이전이면 Track B를 먼저 끝내고 Track A를 뒤로 미뤄야 합니다.
**두 트랙의 순서가 여기서 결정됩니다.**

### 이후

1. **가격 결재를 대행사가 하는가, 지자체가 하는가?**
   대행사면 지금 요금제로 갑니다. 지자체면 판매 경로를 조달 절차로 다시 짜야 하고,
   `enterprise`가 주력이 됩니다. → 대행사 5곳 인터뷰 필요.
   **파일럿과 무관하게 병행 가능하며, 기다릴 이유가 없습니다.**

2. **진단 채점표를 검증할 과거 데이터를 구할 수 있는가?**
   과거 축제 10~20건의 기획서와 결과보고서가 필요합니다.
   못 구하면 진단은 영구히 체크리스트 모드로 남습니다. 그것도 유효한 결론입니다.

3. **결과보고서에 실제로 요구되는 항목이 무엇인가?**
   지자체마다 양식이 다를 수 있습니다. 최근 보고서 실물 5건을 확보해
   F-13의 출력 형식을 거기에 맞춰야 합니다.
   학교축제로는 답이 안 나옵니다 — 학생회는 지자체 보고 의무가 없습니다.

4. **관객 QR 참여율이 몇 %면 "성공"인가?**

   지역 축제보다 참여율이 높게 나올 가능성이 큽니다.
   그 편차를 감안해 해석해야 합니다 — 여기서 3%가 나왔다고
   지역 축제에서도 3%가 나온다는 뜻은 아닙니다.
