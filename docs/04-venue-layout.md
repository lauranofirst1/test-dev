# 행사장 설계 `/festivals/{id}/layout`

기획서(5.2)에서 정한 **숫자**를 실제 **공간**으로 옮기는 화면입니다.
프로그램·부스·시설·인력을 지도 위에 배치하고, 동선을 그리고,
그 결과로 예산과 인력 배치를 자동 산출합니다.

이 화면의 출력은 사전 진단(5.4)의 혼잡/수용 안정성과 운영 준비도 계산에 직접 들어갑니다.
배치도가 있으면 `venue_capacity` 숫자 하나로 추정하던 것을 **존별 면적·수용력 합계와
동선 병목**으로 대체합니다.

**편집 모드** — 상단 토글로 전환합니다.

| 모드 | 하는 일 |
|---|---|
| 배치도 편집 | 존·노드를 놓고 크기와 위치를 조정 |
| 동선 편집 | 노드 사이를 이어 주동선·보조동선·비상동선을 그림 |
| 혼잡 히트맵 | 시간 슬라이더에 따라 존별 추정 밀도를 색으로 표시 (읽기 전용) |
| 기획서 기반 배치 생성 | `planned_*` 값으로 초기 배치안을 자동 생성 |

## 2. 좌표와 단위

캔버스는 **실제 미터 좌표**를 씁니다. 픽셀이 아니라 미터로 저장해야
면적 대비 수용 인원과 동선 폭을 계산할 수 있기 때문입니다.

- `venue_layouts.width_m` / `height_m` — 부지 크기
- 노드·존은 `x_m`, `y_m`, `w_m`, `h_m` (좌상단 기준)
- 화면 배율은 클라이언트가 계산하며 저장하지 않습니다
- 부지 크기를 모르면 예상 방문객 기준 기본값을 제안합니다
  (일 8,000명 → 1인당 3㎡ 가정 → 약 160m × 150m)

## 3. 팔레트

| 그룹 | 항목 | 노드 유형 |
|---|---|---|
| 프로그램 | 공연, 체험, 전시, 이벤트 | `program` |
| 부스 | 공연무대, 체험부스, 판매부스, 음료부스, 지역상점 | `booth` |
| 시설 | 운영본부, 안내소, 화장실, 의무실, 수유실, 물품보관, 주차, 출입구 | `facility` |
| 인력 | 안전요원, 안내요원, 자원봉사, 통역 | `staff_post` |

**`booth` 노드는 `booths` 테이블과 1:1로 연결됩니다.**
지도에서 부스를 놓으면 실제 부스 레코드가 생기고, 운영 대시보드(7장)와
QR 지급(8장)에서 그대로 쓰입니다. 지도와 부스 목록이 따로 놀지 않게 하기 위함입니다.

`program` / `facility` / `staff_post`는 배치 전용 노드이며 부스 레코드를 만들지 않습니다.

## 4. 인스펙터 (노드 속성)

| 필드 | 대상 | 설명 |
|---|---|---|
| 이름 | 전체 | 지도 라벨 |
| 유형 | booth | `booth_type` enum (7.3과 동일) |
| 운영 시간 | booth, program | 축제 운영시간 범위 안이어야 함 |
| 연결 프로그램 | booth | 같은 레이아웃의 `program` 노드 참조 |
| 인원 규모 | 전체 | 동시 수용 인원(명) |
| 수용 인원 | 전체 | 면적으로 자동 계산된 값. 직접 입력으로 덮어쓸 수 있음 |
| 필요 인력 | 전체 | 운영에 필요한 인원(명) |
| 예산 | 전체 | 이 노드에 배정한 금액(원) |
| QR 체험존 사용 | booth | 켜면 이 부스에 모바일 체험 화면을 붙임 ([05-booth-experience.md](05-booth-experience.md)) |
| 메모 | 전체 | 자유 텍스트 |

**면적 기반 수용 인원 자동 계산**

```
권장 수용 인원 = floor(면적_m2 / 1인당_점유면적)
```

| 노드 유형 | 1인당 점유면적 | 근거 |
|---|---|---|
| 공연무대 관람 | 0.5 ㎡/인 | 서서 관람하는 밀집 구역 |
| 체험·전시 | 1.5 ㎡/인 | 활동 공간 필요 |
| 먹거리·휴게 | 2.0 ㎡/인 | 테이블·착석 |
| 통로·대기 | 1.0 ㎡/인 | 보행 여유 |

이 계수는 보행자 밀도 등급(Level of Service) 관행을 단순화한 **FestaFlow 추정 기준**이며,
실측이나 법정 기준이 아닙니다. 화면에도 그렇게 표시합니다.
소방·건축 관련 법정 수용 인원은 별도 검토가 필요하다는 안내를 함께 노출합니다.

## 5. 존 (Zone)

존은 노드를 묶는 구역입니다. 스크린샷의 `A. MAIN STAGE ZONE`처럼
코드(A, B, C…)와 이름, 성격을 가집니다.

| 존 성격 | 용도 |
|---|---|
| `stage` | 공연·무대 |
| `food` | 먹거리 |
| `experience` | 체험·전시 |
| `market` | 지역상점·판매 |
| `rest` | 휴게 |
| `ops` | 운영·안전 |
| `entry` | 출입·주차 |

**존 요약 카드** — 캔버스 하단에 존마다 표시합니다.

- 포함 시설 수
- 예상 동시체류 인원 (현재 시간 슬라이더 기준)
- 혼잡도 배지 `LOW` / `NORMAL` / `HIGH`

혼잡도는 `존 추정 체류 인원 ÷ 존 면적`으로 계산한 밀도를 등급화합니다.

| 밀도 (인/㎡) | 배지 |
|---|---|
| 0.5 이하 | LOW |
| 0.5 초과 1.5 이하 | NORMAL |
| 1.5 초과 | HIGH |

## 6. 동선

동선은 노드와 노드를 잇는 경로입니다.

| 종류 | 표시 | 용도 |
|---|---|---|
| `main` | 굵은 실선 | 주동선. 입구 → 주요 존 |
| `sub` | 가는 실선 | 보조동선 |
| `emergency` | 점선 | 비상 대피 동선 |

각 동선은 **폭(m)** 과 **예상 통행 비중**을 가집니다.

**병목 계산**

```
시간당 통과 가능 인원 = 폭_m × 4,000명/시간/m
```

보행 유량 관행값(약 1.1명/m/초)을 시간당으로 환산한 **추정치**입니다.
예상 통행 인원이 이 값을 넘으면 병목으로 표시합니다.

```
병목 지수 = 예상 시간당 통행 인원 ÷ 통과 가능 인원
```

| 병목 지수 | 표시 |
|---|---|
| 0.7 이하 | 여유 |
| 0.7 초과 1.0 이하 | 주의 |
| 1.0 초과 | 병목 |

비상동선은 별도 규칙을 적용합니다. **폭 3m 미만이거나 출입구까지 이어지지 않으면
무조건 경고**입니다. 축제 안전에서 대피 경로는 혼잡도와 성격이 다른 문제이기 때문입니다.

## 7. 혼잡 히트맵과 시간 슬라이더

운영시간(예: 10:00–23:00)을 30분 단위로 나눠 시간대별 존 밀도를 추정합니다.

```
시간대 t의 존 z 체류 인원
  = 일 예상 방문객
  × 시간대 분포[t]
  × 존 매력도[z]
  × 평균 체류시간[z] / 30분
```

- **시간대 분포** — 티맵 관심지점 일별 집계(`tmapTotalTarItsBroDDList` / `tmapFoodTarItsBroDDList`)의
  지역 실제 방문 패턴을 1순위로 씁니다. 식음료와 그 외가 분리돼 있어
  **먹거리 존과 체험 존에 다른 곡선**을 적용합니다.
  데이터가 없으면 축제 유형별 기본 곡선(주간형/야간형/가족형)으로 폴백하고,
  `program` 노드의 운영 시간이 있으면 그 시간대에 가중치를 더합니다
- **존 매력도** — 존에 배치된 부스 수와 프로그램 규모로 정규화
- **평균 체류시간** — 관광지별 관광 소요시간(`tarTursmRqmtList`)의 지역 값을 기준선으로 씁니다.
  없으면 존 성격별 기본값(무대 40분, 먹거리 30분, 체험 20분, 휴게 15분)으로 폴백합니다.
  화면에는 어느 쪽을 썼는지 표시합니다

**이 히트맵은 시뮬레이션 추정입니다.** 실측 데이터가 아니며,
화면 상단에 그 사실을 고정 배너로 표시합니다.
운영 중 실제 참여 편중은 운영 대시보드(7.1)의 QR 완료 기반 지표에서 확인합니다.
설계 단계의 추정과 운영 중 실측 proxy를 같은 화면에서 섞지 않습니다.

## 8. 기획서 기반 배치 생성

`planned_*` 값과 예상 방문객으로 초기 배치안을 만듭니다. 규칙 기반이며 AI를 쓰지 않습니다.

1. 부지를 존 성격별로 분할 — 무대 30%, 먹거리 20%, 체험 20%, 상점 15%, 휴게 10%, 운영 5%
2. `planned_performance` → `stage` 존에 공연무대 노드
   `planned_food` → `food` 존에 음료·먹거리 부스
   `planned_experience` → `experience` 존에 체험부스
   `planned_local_shop` → `market` 존에 지역상점
   `planned_tour_info` → `entry` 인근에 안내소
3. 필수 시설(§10) 중 누락분을 자동 배치
4. 입구 → 무대 → 먹거리 → 체험 → 상점 → 출구 순으로 주동선 연결
5. 존 면적을 예상 동시체류 인원에 맞춰 조정

생성 결과는 **초안**이며 모든 노드를 자유롭게 옮길 수 있습니다.
이미 배치도가 있으면 덮어쓰기 전에 확인을 받습니다.

## 9. 공간 설계 체크

저장할 때마다 규칙을 돌려 경고를 냅니다. 전부 설명 가능한 규칙이며 차단이 아니라 경고입니다.

| 코드 | 조건 | 메시지 |
|---|---|---|
| `ZONE_OVERCROWDED` | 존 밀도 1.5인/㎡ 초과 | "{존}의 예상 밀도가 높습니다. 면적을 넓히거나 부스를 분산하세요." |
| `PATH_BOTTLENECK` | 병목 지수 1.0 초과 | "{동선}이 예상 통행량을 감당하지 못합니다. 폭을 넓히거나 우회로를 추가하세요." |
| `EMERGENCY_PATH_MISSING` | 비상동선이 출입구에 닿지 않음 | "비상 대피 동선이 출입구까지 연결되지 않았습니다." |
| `EMERGENCY_PATH_NARROW` | 비상동선 폭 3m 미만 | "비상 대피 동선 폭이 3m 미만입니다." |
| `SAFETY_STAFF_SHORT` | 안전요원 노드 수 < 존 수 | "안전요원이 배치되지 않은 존이 있습니다." |
| `ZONE_ADJACENCY` | `stage`와 `rest`가 인접 | "무대 소음이 휴게 구역에 영향을 줄 수 있습니다." |
| `FOOD_FAR_FROM_REST` | 먹거리 존에서 가장 가까운 휴게 존까지 80m 초과 | "먹거리 구역과 휴게 구역이 멀리 떨어져 있습니다." |
| `BUDGET_OVER` | 노드 예산 합계 > `total_budget` | "배치 예산이 총예산을 {금액}원 초과했습니다." |
| `STAFF_OVER` | 피크 시간 필요 인력 > 확보 인력 | "{시각} 기준 인력이 {N}명 부족합니다." |
| `NODE_OUTSIDE` | 노드가 부지 밖 | "{노드}가 부지 범위를 벗어났습니다." |
| `NODE_OVERLAP` | 노드끼리 겹침 | "{노드}와 {노드}가 겹칩니다." |

## 10. 필수 시설 체크

축제 규모에 따라 있어야 할 시설을 체크리스트로 보여줍니다 (스크린샷의 `6/8`).

| 시설 | 필수 조건 |
|---|---|
| 주 출입구 | 항상 |
| 운영본부 | 항상 |
| 안내소 | 항상 |
| 화장실 | 항상 (일 방문객 500명당 1개소 권장) |
| 의무실 | 일 예상 방문객 3,000명 이상 |
| 수유실 | 가족 타깃이 `target_segments`에 있을 때 |
| 물품보관소 | 일 예상 방문객 5,000명 이상 |
| 흡연구역 | 항상 |

충족 수 / 전체 수를 표시하고, 미충족 항목은 클릭하면 해당 시설이 팔레트에서 강조됩니다.
이 목록은 운영 편의를 위한 **권장 기준**이며 법정 설치 기준이 아니라는 문구를 함께 표시합니다.

## 11. 예산과 인력 배치

노드에 입력한 예산·인력이 합산되어 두 개의 요약을 만듭니다.

**예산 배치**

| 항목 | 값 |
|---|---|
| 총예산 | `festivals.total_budget` |
| 배치 합계 | 노드 예산 합 |
| 미배정 | 총예산 − 배치 합계 |
| 존별 비중 | 존 예산 합 ÷ 배치 합계 |

배치 합계가 총예산을 넘으면 `BUDGET_OVER` 경고를 냅니다.

**인력 배치**

노드마다 `필요 인력`과 `운영 시간`이 있으므로, 30분 단위로 동시 필요 인력을 계산합니다.

```
시각 t의 필요 인력 = Σ (운영 시간이 t를 포함하는 노드의 필요 인력)
확보 인력 = staff_count + volunteer_count + safety_staff_count  (5.2 기획 입력값)
```

피크 시각의 필요 인력이 확보 인력을 넘으면 `STAFF_OVER` 경고와 함께
**시간대별 인력 곡선**을 표시합니다. 교대 계획을 세울 때 쓰는 그림입니다.

## 12. 사전 진단 연동

배치도가 있으면 진단(5.4)의 두 항목이 더 정확해집니다.

**혼잡/수용 안정성 (30점)** — 일일 수용력 산정 우선순위를 다음으로 바꿉니다.

| 순위 | 근거 | 계산 |
|---|---|---|
| 1 | **배치도** | Σ(존 권장 수용 인원) × 하루 2회전 |
| 2 | 기획 입력 `venue_capacity` | 동시 수용 인원 × 하루 2회전 |
| 3 | TourAPI 기반 추정 | `max(3000, 2500 + √콘텐츠수 × 300)` |

배치도 기준을 쓸 때는 동선 병목도 함께 반영합니다.
병목 동선이 하나라도 있으면 혼잡 점수에서 2점, 비상동선 경고가 있으면 3점을 감점합니다.
계산 근거에 어떤 순위의 데이터를 썼는지, 어떤 감점이 있었는지 그대로 씁니다.

**운영 준비도 (10점)** — 필수 시설 체크 충족률과 인력 배치 충족 여부를
기존 "운영 인력·안전 계획" 항목의 판단 근거로 사용합니다.
계획 텍스트가 비어 있어도 배치도에 실제 시설과 인력이 놓여 있으면 점수를 인정합니다.

배치도가 없으면 기존 로직 그대로 동작합니다. 배치도는 **선택 사항**입니다.

## 13. 버전과 저장

- 저장은 명시적입니다(자동 저장 없음). 편집 중 이탈 시 경고합니다.
- `venue_layouts.version`을 두고, 저장할 때마다 직전 상태를 `venue_layout_snapshots`에
  JSON으로 1건 남깁니다. 되돌리기는 최근 10개까지 지원합니다.
- 축제가 `live` 상태로 넘어간 뒤의 편집은 경고만 하고 막지는 않습니다.
  현장에서 배치가 바뀌는 일은 실제로 자주 일어나기 때문입니다.
- `booth` 노드를 지도에서 삭제하면 부스 레코드는 **아카이브**되며,
  이미 지급 이력이 있으면 "이 부스에 지급 이력 N건이 있습니다"를 먼저 안내합니다.
