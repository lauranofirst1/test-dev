## 1. 🚨 우리 설계와 정면 충돌하는 규정

### 로컬 DB 캐싱이 심사 불이익 대상입니다

> "한국관광공사 OpenAPI 서비스는 데이터 동기화 오류 방지를 위해 로컬 DB 저장 방식이 아닌
> **실시간 호출 방식으로 활용하실 것을 강력히 권고**드립니다."
>
> "**실제 API 호출 내역을 검증**합니다. 로컬 DB 저장 방식을 사용하여 서비스 개발 기간 내
> API 호출 이력이 확인되지 않을 경우, **심사에서 불이익을 받을 수 있으니** 각별히 유의"

우리는 `tourism_snapshots`에 **TTL 7일로 캐시**하고, 캐시 히트 시 **호출을 0회**로 만드는
설계를 했습니다(`docs/07-tourapi-catalog.md` §0). 일 1,000건 한도 대응으로는 옳지만,
**공모전 심사 기준으로는 정확히 불이익 사유**입니다.

**해결 방안 (선택)**

| 안 | 내용 | 평가 |
|---|---|---|
| **A. 진단 실행 시 항상 실시간 호출** | 스냅샷은 **폴백·이력 보존용으로만** 쓰고, 진단을 누르면 무조건 API를 부름 | ✅ **권장.** 호출 이력이 남고 캐시 이점도 유지 |
| B. TTL을 대폭 단축 (7일 → 1시간) | 캐시는 유지하되 호출이 자주 발생 | 절충안. 한도 소진 위험 |
| C. 캐시 제거 | 규정에 완전히 부합 | 한도 1,000건 소진 위험 |
| D. 별도 신청서 제출 | `tourapi@knto.or.kr`로 사전 문의 | 시간이 걸림 |

**A안으로 갑니다.** 구현은 이렇습니다.

- 진단 실행 = **항상 API 호출**. 응답을 스냅샷에 기록
- 스냅샷은 **API가 실패했을 때만** 읽습니다 (3단계 폴백의 ②)
- 결과적으로 진단 1회 = API 4~12회 호출이 **반드시** 발생
- 개발 기간 내 호출 이력이 인증키에 그대로 남습니다

한도 계산: 진단 1회 = 최대 12회. 일 1,000건 ÷ 12 = **하루 83회 진단** 가능.
개발·시연 용도로는 충분합니다.

> `docs/07-tourapi-catalog.md` §0의 "캐시 히트 시 0회" 설명은
> **공모전 기간 동안은 적용하지 않습니다.** 수상 이후 운영 단계에서 다시 켭니다.

## 2. 반드시 준비해야 하는 것

### 2.1 접속 가능한 웹 URL

- 웹은 **URL만 제출**하면 됩니다 (앱은 스토어 등록·승인 필수 → 우리는 웹이라 유리)
- **서버비 지원 없음.** AWS·GCP 프리티어 권장
- 심사 기간(10월 말)까지 계속 떠 있어야 합니다

### 2.2 테스트 계정 — 형식이 지정돼 있습니다

로그인이 필요한 서비스는 **개인 계정 제출 불가**. 아래 형식만 허용됩니다.

```
일반계정   ID: openapi          PW: 2026openapi!
이메일계정  ID: openapi@도메인   PW: 2026openapi!
```

**우리 서비스는 로그인 구조가 셋입니다** — 기획자(계정), 스태프(축제별 접근 코드),
관객(익명). 심사위원이 전부 볼 수 있어야 하므로:

| 역할 | 심사용 처리 |
|---|---|
| 기획자 | `openapi / 2026openapi!` 테스트 계정 생성 |
| 운영·부스 스태프 | 데모 축제의 접근 코드를 **기능설명서에 명시** |
| 관객 | 로그인 불필요 — 데모 축제 `/join/{id}` URL을 명시 |

**데모 축제 1건을 심사용으로 미리 채워둬야 합니다.** 부스·미션·참여 이력·진단 결과까지
들어 있어야 심사위원이 빈 화면을 보지 않습니다.

### 2.3 인증키 정보 제출

- 활용한 OpenAPI의 **인코딩·디코딩 키 일체** 제출
- 대표 1개 API에 대해 **운영계정 신청**(선택)
- 이 키로 **개발 기간(7/27~9/21) 내 호출 건수를 검증**합니다

**지금 키를 못 받고 있으면 이게 최우선 리스크입니다.**
호출 이력이 0이면 "OpenAPI 필수 활용" 요건 미충족으로 심사 제외될 수 있습니다.

### 2.4 지정과제 — **9번 확정**

> **9. 축제 수요 예측 실패 및 주관적 경험 의존형 기획으로 인한
> 예산 낭비 리스크 존재 및 대규모 관광객 쏠림에 따른 축제 만족도 저하**

공고문 `[붙임]`의 예시 서비스와 FestaFlow를 대조하면 이렇습니다.

| 공고문 예시 | FestaFlow |
|---|---|
| 타깃: 지자체 및 **축제 위탁사 실무자** | 1차 세그먼트: **축제 대행사 담당자** — 같은 말 |
| 주제: 축제의 사전 흥행 가능성을 예측·진단 | 사전 진단 (5개 항목 100점) |
| 기능 ①: 축제 개요 및 프로그램 세부 계획 입력 | 5.2 축제 기획 기록 |
| 기능 ②: 데이터 기반 흥행도 도출 + 기획 보완 피드백 리포트 | 5.4 진단 결과 + 항목별 개선 제안 |
| 해결과제 후반: 대규모 관광객 **쏠림**에 따른 만족도 저하 | 7.1 참여 편중 인사이트 + 7.2 보상 캠페인 |

**다른 과제를 검토했지만 전부 어긋납니다.**

| 과제 | 왜 아닌가 |
|---|---|
| 2 오버투어리즘 분산 | 타깃이 자유여행객, 결과물이 코스 추천. 우리는 운영자 도구 |
| 7 관광 상품 기획 자동화 | 여행상품이지 축제가 아님 |
| 10 관광 성장 전략 | 지자체 정책보고서. 축제 특정이 아님 |

**결합 전략** — 지정과제는 9번 하나만 선택하되,
기능설명서에 **2번(오버투어리즘 분산) 요소를 결합**했다고 명시합니다.
9번 해결과제 자체에 "관광객 쏠림"이 들어 있어 자연스럽게 이어집니다.

### 2.4.1 🚨 과제 9와 충돌하는 우리 결정 — 진단 점수 봉인

과제 9의 핵심 기능은 **"데이터 기반 축제 흥행도 도출"** 이고,
예시 서비스명도 "축제 흥행 **예보** 서비스", 해시태그도 `#사전 수요 예측`입니다.

그런데 우리는 **채점표가 검증되기 전까지 점수를 공개하지 않기로**
결정했습니다(`docs/01-product-spec.md` §5.4 — `checklist` 모드).

공고문은 이렇게 경고합니다.

> 과제 충족 기준(과제에 부합하는 서비스 기획, 공사 OpenAPI 필수 활용 등)에
> 부합되지 않는다고 판단될 경우 **심사 대상에서 제외**될 수 있습니다.

**점수를 안 보여주면 "흥행도 도출"이라는 과제 핵심 기능이 화면에 없습니다.**
심사위원이 과제 미충족으로 판단할 위험이 실재합니다.

**결정 — 공모전 출품 버전은 `score` 모드로 켭니다.** 대신 정직함을 이렇게 지킵니다.

1. 점수 옆에 **항상 계산 근거**를 붙입니다 (이미 그렇게 설계돼 있음)
2. 지표별로 **조회값·추정값·폴백 여부**를 표기합니다 (이미 설계돼 있음)
3. 화면에 명시합니다 — *"이 점수는 한국관광공사 데이터 N종으로 산출한 **준비도 상대 지표**이며,
   흥행을 보증하지 않습니다. 과거 축제 데이터 기반 검증은 진행 예정입니다."*
4. **백테스트 계획을 기능설명서의 "발전계획"에 명시**합니다 —
   `rubric_calibrations` 테이블과 검증 절차가 이미 설계돼 있다는 것이 오히려 강점입니다

점수를 숨기는 것보다 **"점수의 한계를 아는 채로 보여주는 것"** 이 과제 부합성과
기획력(30점) 양쪽에서 낫습니다. 대부분의 팀은 근거 없는 점수를 그냥 띄울 겁니다.

### 2.5 해시태그 — 예측만이 아니라 루프

공고문 예시(과제 9)는 `#축제/행사 기획` `#사전 수요 예측` `#보완 피드백 제공` `#데이터 기반`입니다.
앞의 셋은 그대로 쓰고, **우리만의 차별점을 두 개 더 얹습니다.**

| 해시태그 | 연계 기능 | 성격 |
|---|---|---|
| `#축제기획진단` | TourAPI 12종 기반 5개 항목 준비도 진단 | 예시 준용 |
| `#사전수요예측` | 집중률 30일 예측 + 방문자수 + 수요 강도 | 예시 준용 |
| `#보완피드백` | 항목별 계산 근거 + 개선 제안 + 직전 대비 변화 | 예시 준용 |
| **`#쏠림실측분산`** | QR 완료 기반 부스별 편중 지표 + 한시 보상 캠페인 | **자체** |
| **`#예측실측교정`** | 사후 리포트가 예측과 실측을 대조해 다음 기획을 교정 | **자체 — 최대 차별점** |

### 2.5.1 차별화 스토리 — "검증되는 예보"

다른 팀은 대부분 **사전 예측만** 만들 겁니다. 예보는 맞았는지 알 수 없으면 점술입니다.

FestaFlow는 한 바퀴를 돕니다.

```
① 사전 진단      TourAPI 12종으로 쏠림·수용력·연계성을 예측
        ↓
② 당일 실측      QR 완료로 부스별 쏠림을 실제로 측정, 보상으로 분산
        ↓
③ 사후 대조      예측과 실측을 나란히 놓고 다음 기획을 교정
        ↓
      ①로 되돌아감 (rubric_calibrations에 누적)
```

**"예산 낭비 리스크"(과제 9)를 줄이는 건 예측이 아니라 예측의 정확도**이고,
정확도는 실측 없이는 올라가지 않습니다. 이 논리가 서비스 기획력(30점)과
발전성(20점)을 동시에 겨냥합니다.

기능설명서 "서비스 차별성"에 이 루프 그림을 넣으세요.

### 2.5.2 QR 참여 기능을 과제 9에 연결하는 법

주의할 점 — **QR 스탬프와 조각 보드는 과제 9와 직접 연결이 약해 보입니다.**
심사위원이 "이건 다른 과제 아닌가"라고 볼 수 있습니다. 기능설명서에서
아래 연결을 **명시적으로** 써야 합니다.

| 기능 | 과제 9의 어느 문장에 걸리는가 |
|---|---|
| QR 스탬프 지급 | 쏠림을 **측정**하는 유일한 수단. 측정 없이는 분산도 교정도 불가 |
| 부스별 편중 지표 | "대규모 관광객 **쏠림**에 따른 축제 만족도 저하" 직접 대응 |
| 조각 수집 보드 | 관객을 저참여 부스로 유도 → **쏠림 완화 장치** |
| 보상 캠페인 | 쏠림 발생 시 실시간 개입 수단 |
| 사후 리포트 | "주관적 경험 의존형 기획" → **데이터 의존형으로 전환** |

즉 QR은 놀이 기능이 아니라 **쏠림 측정 센서**라고 설명해야 합니다.

### 2.6 출처 표기 — 규정이 까다롭습니다

| | 표기 |
|---|---|
| ✅ 허용 | `출처: ⓒ한국관광공사` / `출처: ⓒ한국관광콘텐츠랩` |
| ❌ 금지 | `TourAPI` 단독 표기 |
| ❌ 금지 | 서비스명·로고에 "한국관광공사", "KTO" 사용 |
| ❌ 금지 | 공사 공식 CI/BI 로고 이미지 (텍스트 표기만 허용) |

**우리 문서와 UI에 `TourAPI`라는 표기가 여러 곳에 있습니다.**
사용자에게 보이는 화면(진단 결과의 데이터 출처 문자열, 리포트 푸터)은
`출처: ⓒ한국관광공사`로 통일해야 합니다. 내부 문서·코드는 무관합니다.

### 2.7 위치기반서비스사업자 신고 — 해당 없음

- 개인위치정보를 **서버로 전송하면** 신고 대상
- FestaFlow는 **GPS를 쓰지 않습니다.** QR 스캔 기반이고, 좌표는 관광지 정보(`mapx`/`mapy`)를
  표시하는 용도라 개인위치정보가 아닙니다
- **단, 이 판단을 기능설명서에 명시**해 두는 게 안전합니다

## 5. 5주에 맞춘 구현 범위

1차 심사는 **구동 안정성과 완성도**를 봅니다. 기능이 많은 것보다
**적은 기능이 확실히 도는 게** 유리합니다.

### 반드시 (9/21까지)

우선순위는 **과제 9 부합성** 순입니다. 시간이 모자라면 아래에서부터 자릅니다.

| # | 기능 | 과제 9 연결 | 심사 기여 |
|---|---|---|---|
| 1 | **사전 진단 — TourAPI 실시간 호출 + 점수 공개** | 과제 핵심 "흥행도 도출" | 데이터 20 + 과제 부합성 |
| 2 | 축제 기획 입력 (개요 + 프로그램 계획) | 과제 기능 ① | 구현성 |
| 3 | 진단 리포트 (근거 + 개선 제안 + 직전 대비) | 과제 기능 ② "보완 피드백" | 구현성·기획력 |
| 4 | QR 스탬프 지급 → **쏠림 측정** | "관광객 쏠림" 대응 | 독창성 |
| 5 | 부스별 편중 지표 + 조각 보드 | 쏠림 분산 장치 | 독창성 |
| 6 | 사후 리포트 (예측 vs 실측 대조) | **예측→실측→교정 루프** | 기획력·발전성 |
| 7 | 데모 축제 1건 (데이터 채워진 상태) | — | 심사위원 체험 |

**1~3번이 과제 부합성의 근간입니다.** 이게 없으면 심사 대상에서 제외될 수 있으므로
어떤 일이 있어도 완성해야 합니다. 4~6은 차별점이고, 7은 심사 편의입니다.
