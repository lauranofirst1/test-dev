# 한국관광공사 OpenAPI 카탈로그

출처: [한국관광 콘텐츠랩 OpenAPI 목록](https://api.visitkorea.or.kr/#/useUtilExercises) (2026-08 기준 **총 26건**)
공모전 제출작은 이 목록의 API를 사용해야 합니다.

> 호출 규격은 §6에 확정돼 있습니다. 오퍼레이션별 상세 파라미터·응답 필드는
> 각 API 활용신청 승인 후 §7에 채워 넣습니다.

## 0. 호출 규격 (확정)

### Base URL

```
https://apis.data.go.kr/B551011/{서비스명}/{오퍼레이션}
```

`B551011`은 한국관광공사 기관 코드로 26개 API 전부 공통입니다.
문서에 `http://`도 나오지만 **`https://`를 씁니다.**

### 공통 요청 파라미터

| 파라미터 | 필수 | 값 | 비고 |
|---|---|---|---|
| `serviceKey` | ✔ | 발급 인증키 | 아래 인코딩 주의 |
| `numOfRows` | | 한 페이지 결과 수 | 기본 10 |
| `pageNo` | | 페이지 번호 | 기본 1 |
| `MobileOS` | ✔ | `ETC` / `AND` / `IOS` / `WIN` | 서버 호출은 `ETC` |
| `MobileApp` | ✔ | 서비스명 | **활용 통계 산출용. 반드시 기재** |
| `_type` | | `json` | **없으면 XML로 옵니다** |

### 호출 예시

```
GET https://apis.data.go.kr/B551011/KorService2/areaBasedList2
      ?serviceKey={KEY}
      &numOfRows=100
      &pageNo=1
      &MobileOS=ETC
      &MobileApp=FestaFlow
      &_type=json
```

`MobileApp`은 **`FestaFlow`로 고정**합니다. 영문이라 URL 인코딩이 필요 없습니다.
(국문 서비스명을 쓸 경우에만 `URLEncoder.encode(name, "UTF-8")`가 필요합니다.
우리는 해당 없음.)

### `serviceKey` 인코딩 함정

공공데이터포털은 인증키를 **Encoding / Decoding 두 벌**로 줍니다.

- HTTP 클라이언트가 쿼리스트링을 다시 인코딩하면 `%2B`가 `%252B`가 되어 **인증 실패**합니다
- 그래서 서버는 환경변수로 받은 키를 `unquote`로 한 번 정규화한 뒤,
  쿼리 빌더에 넘기지 말고 **직접 문자열로 조립**합니다

```python
# apps/api/src/festaflow/services/tourapi.py
from urllib.parse import unquote, quote

raw = os.environ["KTO_TOUR_API_KEY"]
key = quote(unquote(raw), safe="")   # 이중 인코딩 방지
url = f"{BASE}/{service}/{op}?serviceKey={key}&{other_params}"
```

`docs/01-product-spec.md` §6.1의 "URL 인코딩되어 들어온 키는 unquote로 정규화"가
이 이야기입니다.

### 트래픽 제한 — 설계에 직접 걸립니다

| 계정 | 한도 | 승인 |
|---|---|---|
| **개발계정** | **일 1,000건** | 자동 승인, 신청 후 약 10분 |
| 운영계정 | 상향 (별도 신청·심사) | 심사 필요 |

한도는 **활용신청 단위**이므로 API마다 따로 계산됩니다.
그래도 진단이 API를 라이브로 때리면 금방 소진됩니다.

> 🚨 **공모전 기간에는 캐시를 끕니다.** 공모전 규정이 "로컬 DB 저장이 아닌
> **실시간 호출 방식**"을 강력히 권고하고, **인증키의 실제 호출 이력을 검증**합니다.
> 캐시 히트로 호출이 0회가 되면 심사 불이익 대상입니다.
> 진단 실행 시 항상 API를 부르고, 스냅샷은 **실패 시 폴백·이력 보존용으로만** 씁니다.
> 상세는 [08-contest-submission.md](08-contest-submission.md) §1.
> 아래 캐시 절감 계산은 **수상 이후 운영 단계** 기준입니다.

**운영 단계에서는 캐시가 한도를 막아 줍니다.** `tourism_snapshots`가
`(지역키 + 기준월 + 공급자)` 단위로 캐시하고 TTL 7일을 둡니다
(`docs/02-data-model.md` §9).

```
진단 1회당 호출 수 (캐시 미스)
  areaCode2          지역코드 해석      1회  ← festivals에 저장돼 재사용
  areaBasedList2     관광 콘텐츠 100건   1회
  수요강도 (체류 21)                    1회
  수요강도 (소비 22)                    1회
  ─────────────────────────────────────────
  합계                                 4회

캐시 히트 시                            0회
```

같은 축제를 일주일에 10번 재진단해도 **4회**입니다. 40회가 아닙니다.
일 1,000건이면 하루 **250개 지역·월 조합**을 새로 조회할 수 있고,
실사용은 그 근처에도 안 갑니다.

**축제 당일에는 TourAPI를 호출하지 않습니다.** 진단은 기획 단계 기능이고,
운영 대시보드·QR 지급·리포트는 전부 자체 DB만 씁니다.
현장에서 한도 소진으로 서비스가 멈추는 시나리오는 없습니다.

§2.2의 확장 API를 붙일 때도 **같은 스냅샷 규칙을 적용**합니다.
API별로 독립 폴백하고, 하나가 한도를 넘겨도 나머지 진단은 계속 계산됩니다.

## 3. 설계 변경 제안

### 3.1 A4 방문자수 — 가장 중요한 변경

지금까지 이 제품의 가장 큰 구조적 약점은 **방문객을 측정하지 않는다**는 것이었습니다
(`docs/pipeline/01-strategy.md` 가정 ①, `03-prd.md` US-19).
`visitor_counts`를 만들어 "남이 센 숫자를 받아 쓴다"로 우회했지만,
그 입력은 운영자의 수동 입력에 의존했습니다.

**A4는 이걸 공식 데이터로 채웁니다.**

```
축제 유입 추정 = 축제 기간 해당 기초지자체 방문자수
               − 직전 4주 같은 요일 평균 방문자수
```

이건 축제장 입구를 센 값이 아니라 **지자체 단위 순증분**이므로,
"축제로 인한 지역 방문 증가"라고 부를 수 있습니다. 축제장 방문객이라고는 못 합니다.
그 차이를 화면 문구에 그대로 씁니다.

**스키마 변경** — `visitor_source` enum에 값 추가:

```sql
ALTER TYPE visitor_source ADD VALUE 'kto_bigdata';
```

우선순위는 `beacon` > `manual_counter` > **`kto_bigdata`** > `partner` > `estimate`.
현장 계수기보다는 낮고 주최측 추산보다는 높습니다 —
지자체 단위라 축제장보다 범위가 넓지만, 추산보다는 근거가 있습니다.

### 3.2 A5 집중률 예측 — 진단 ②를 미래 기반으로

현재 계절 적합도는 **행사 시작 월과 같은 과거 월의 체류 지수**를 정규화한 값입니다.
작년 10월이 붐볐다고 올해 10월이 붐빈다는 보장이 없습니다.

A5는 조회일 기준 **향후 30일 관광객 집중률 예측**을 줍니다.
행사 시작일이 30일 이내면 예측값을 1순위로 쓰고, 그보다 멀면 기존 계절 적합도를 씁니다.
계산 근거에 **어느 쪽을 썼는지 명시**합니다 — 지금 수용력 근거를 명시하는 것과 같은 방식입니다.

### 3.3 A7 연관 관광지 — 진단 ④의 근거 교체

현재 지역 관광 연계성 15점은 이렇습니다.

```
인근 관광자원 수 × 1.5 (최대 9점) + 지역 연계 준비도 × 6 (최대 6점)
```

`지역 연계 준비도`는 `min(0.95, 0.45 + log1p(콘텐츠수) ÷ 10)`이라는 **순수 추정치**입니다.
근거가 없다고 검토에서 지적한 항목입니다.

A7은 중심관광지와의 **실제 연결성 순위**를 줍니다. 이걸로 바꾸면:

```
연계 점수 = 축제 장소 인근 관광지가 지역 연관 관광지 상위 50위에 몇 개 포함되는가
           + 그 관광지들의 연결성 순위 가중
```

FestaFlow 추정치가 아니라 **관광공사 데이터**가 근거가 됩니다.
`tourism_snapshots.source_note`의 "추정치" 표기가 하나 줄어듭니다.

### 3.4 D2 관광사진 — 스탬프 보드 이미지

`stamp_boards.image_url` 기본값이 `/images/chuncheon-stamp-board.png` 하드코딩입니다.
D2로 **축제 지역의 실제 관광사진**을 가져와 후보로 제시하면,
운영자가 이미지를 준비할 필요가 없어지고 지역색이 살아납니다.

조각을 모아 완성되는 그림이 **그 지역의 실제 풍경**이라는 건
수집 동기 측면에서도 하드코딩 이미지보다 낫습니다.

### 3.5 D1 오디오 가이드 — `info` 체험의 실제 콘텐츠

부스 QR 체험 `info` 유형은 지금 운영자가 안내 텍스트를 직접 씁니다.
D1은 4개 국어 음성·대본·사진을 줍니다.

관광안내소 부스에서 QR을 찍으면 **인근 관광지의 실제 오디오 해설**이 재생되고,
다 들으면 조각이 열리는 구조가 됩니다. `min_dwell_seconds`가
오디오 길이로 자연스럽게 정해집니다.

2026 관광데이터 활용 공모전(웹·앱 개발 부문)은 관광 데이터 활용도가 심사 요소입니다.

전략 문서의 "안 하는 것"에 다국어·해외가 명시돼 있고 나머지는 축제 운영과 무관합니다.

### 신청 방법

1. [공공데이터포털](https://www.data.go.kr) 로그인
2. 서비스 ID 또는 국문명으로 검색 → **활용신청**
3. 활용목적은 "공모전 출품작 개발" 등으로 기재
4. 약 10분 뒤 **마이페이지 > 오픈API > 개발계정**에서 인증키 확인
5. `.env`에 **하나의 키**를 넣고 전 서비스에 공용으로 사용

```bash
KTO_API_KEY=<Decoding 키>        # 인코딩·디코딩 두 벌 중 Decoding 쪽
KTO_BASE_URL=https://apis.data.go.kr/B551011
KTO_MOBILE_APP=FestaFlow
```

> 포털이 주는 **Encoding / Decoding 두 벌 중 Decoding 키**를 넣고,
> 코드에서 `quote(unquote(key), safe="")`로 한 번 정규화하세요(§0).
> Encoding 키를 그대로 넣으면 HTTP 클라이언트가 다시 인코딩해 `%2B`가 `%252B`가 되면서
> 인증이 깨집니다.

## 5.1 신청 후 할 일

1. **명세 채우기** — 각 API의 오퍼레이션 파라미터·응답 필드를 §8 형식으로 기록

### 6.2 에러 처리 — 파서 함정이 하나 있습니다

**포털 레벨 에러는 `_type=json`을 붙여도 XML로 옵니다.**

```xml
<OpenAPI_ServiceResponse>
  <cmmMsgHeader>
    <errMsg>SERVICE ERROR</errMsg>
    <returnAuthMsg>SERVICE_KEY_IS_NOT_REGISTERED_ERROR</returnAuthMsg>
    <returnReasonCode>30</returnReasonCode>
  </cmmMsgHeader>
</OpenAPI_ServiceResponse>
```

JSON 파싱이 실패하면 곧바로 예외를 던지면 안 됩니다.
**본문에 `OpenAPI_ServiceResponse`가 있는지 먼저 확인**하고 `returnReasonCode`를 읽어야
"왜 실패했는지"를 알 수 있습니다. 아니면 전부 "JSON 파싱 실패"로 뭉개집니다.

에러는 두 층입니다.

- **포털 레벨** — 인증·한도·서비스 존재 여부. XML로 옴
- **제공기관 레벨** — 파라미터·데이터 없음. JSON 본문의 `resultCode`

### 6.3 에러 코드별 대응

| 코드 | 의미 | FestaFlow 처리 |
|---|---|---|
| `00` | 정상 | — |
| **`03`** | **NODATA_ERROR 데이터 없음** | **에러가 아님.** 빈 결과로 정상 처리. 해당 지표만 제외하고 진단 계속 |
| `05` | 서비스 연결실패 | 지수 백오프 3회 재시도 → 실패 시 스냅샷/데모 폴백 |
| `10` `11` | 파라미터 오류 | **우리 버그.** 알림 + 즉시 데모 폴백. 재시도 무의미 |
| `12` | 서비스 없음/폐기 | 알림. 해당 API 비활성화 |
| `20` `30` `31` `32` `33` | 인증·권한·기한·IP | **설정 문제.** 운영 알림 + 데모 폴백. 재시도 무의미 |
| **`22`** | **요청제한 초과** | 해당 API를 **당일 차단**하고 스냅샷만 사용. 대시보드에 잔여 한도 경고 |
| `01` `02` `04` `99` | 애플리케이션·DB·HTTP·기타 | 1회 재시도 → 데모 폴백 |

**`03`(데이터 없음)을 실패로 처리하면 안 됩니다.** 신규 축제 지역이나
데이터가 얇은 기초지자체에서 정상적으로 발생합니다. 이걸 에러로 잡으면
그런 지역은 영원히 데모 데이터만 보게 됩니다.

**`22`(한도 초과)는 재시도하면 안 됩니다.** 자정까지 계속 실패하므로
호출 자체를 차단하고 캐시로 버팁니다.

### 6.4 폴백 단계

```
① 실데이터 호출
     ├─ 03 NODATA ──▶ 해당 지표만 제외, 나머지로 진단 계속
     ├─ 22 한도초과 ─▶ ② 로 (당일 이 API 차단)
     └─ 그 외 실패 ──▶ ②
②  만료된 스냅샷 재사용 (TTL 지났지만 있는 값)
     └─ 없으면 ▶ ③
③  데모 공급자
     └─ 출처에 "데모 대체 데이터(API 연결 실패)" 표기
```

**TTL이 지난 스냅샷을 데모보다 먼저 씁니다.** 일주일 지난 실제 데이터가
지어낸 데모 값보다 낫습니다. 다만 진단 근거에 "N일 전 데이터" 라고 명시합니다.

폴백은 **API별로 독립적**입니다. 방문자수가 죽어도 수요 강도는 실데이터로 갑니다.

## 7. 명세로 확정된 설계 변경

`DataLabService`의 오퍼레이션 6개를 보고 **우리가 지어낸 추정치 셋이
공사 데이터로 대체 가능**해졌습니다. 이건 §3에서 예상하지 못했던 소득입니다.

### 7.1 `tarDecoList` — 혼잡 위험도를 계산에서 조회로

현재 혼잡 위험도는 이렇습니다 (`docs/01-product-spec.md` §6.3).

```
혼잡 위험도 = clamp(0.25 + 수요정규값 × 0.35 + 수용초과정규값 × 0.25, 0, 1)
```

계수 `0.25 / 0.35 / 0.25`에 아무 근거가 없습니다. 검토에서 지적한 항목입니다.
`tarDecoList`는 **관광지별 혼잡도 예측**을 직접 줍니다.

축제 장소 인근 관광지의 혼잡도 예측을 가져와 쓰면,
진단 ② 혼잡/수용 안정성의 혼잡 점수(10점)가 추정이 아니라 조회가 됩니다.

### 7.2 `tarTursmRqmtList` — 체류시간을 실제 값으로

행사장 설계의 혼잡 히트맵(`docs/04-venue-layout.md` §7)은
존 성격별 평균 체류시간을 **제가 정한 기본값**으로 씁니다.

```
무대 40분, 먹거리 30분, 체험 20분, 휴게 15분   ← 근거 없음
```

`tarTursmRqmtList`는 **관광지별 관광 소요시간**을 줍니다.
축제 지역 관광지의 실제 소요시간 분포를 기준선으로 삼으면
히트맵 시뮬레이션의 입력이 실측 기반이 됩니다.

### 7.3 `tmap*ItsBroDDList` — 시간대 분포 곡선을 실제 패턴으로

히트맵의 시간대 분포는 지금 `daytime / night / family` 세 개의
**제가 그린 곡선** 중 하나를 고르는 방식입니다.

티맵 관심지점 일별 집계는 실제 방문 패턴을 줍니다.
식음료(`tmapFoodTarItsBroDDList`)와 그 외(`tmapTotalTarItsBroDDList`)가
분리돼 있어서, **먹거리 존과 체험 존의 시간대 패턴을 따로** 적용할 수 있습니다.
축제 히트맵에 정확히 필요한 구분입니다.

### 7.4 남는 추정치는 하나

| 값 | 이전 | 이후 |
|---|---|---|
| 혼잡 위험도 | FestaFlow 추정 | **`tarDecoList` 조회** |
| 지역 연계 준비도 | FestaFlow 추정 | **`TarRlteTarService1` 연결성** |
| 존 체류시간 | 하드코딩 기본값 | **`tarTursmRqmtList` 기준** |
| 시간대 분포 | 임의 곡선 3종 | **`tmap*` 실제 패턴** |
| 행사장 일일 수용력 | FestaFlow 추정 | **그대로 추정** |

마지막 하나는 남겨두는 게 맞습니다. 행사장 수용력은 **우리가 그린 배치도에서
계산하는 값**이라 공사 데이터에 있을 수가 없습니다.
이건 추정이라고 계속 표기합니다.

### 7.5 스키마 영향

`tourism_snapshots`가 지금 A1(수요 강도) 기준 컬럼만 갖고 있습니다
(`docs/02-data-model.md` §9). 위 지표들을 담으려면 확장이 필요합니다.

```sql
ALTER TABLE tourism_snapshots
  ADD COLUMN congestion_forecast NUMERIC(5,4),      -- tarDecoList
  ADD COLUMN avg_dwell_minutes   NUMERIC(6,2),      -- tarTursmRqmtList
  ADD COLUMN hourly_pattern      JSONB,             -- tmap* (식음료/그외 분리)
  ADD COLUMN visitor_counts_raw  JSONB,             -- locgoRegnVisitrDDList
  ADD COLUMN related_spots       JSONB,             -- TarRlteTarService1
  ADD COLUMN hub_spots           JSONB;             -- LocgoHubTarService1
```

`congestion_risk`(추정)와 `congestion_forecast`(조회)를 **둘 다 남깁니다.**
공사 데이터가 없는 지역에서는 기존 추정식으로 폴백해야 하고,
진단 근거에 어느 쪽을 썼는지 표기해야 하기 때문입니다.
수용력 근거를 3순위로 명시하는 것과 같은 방식입니다.

### 7.6 rubric v2

§7.1과 §3.3이 진단 산식의 근거를 바꾸므로 **채점표를 v2로 올립니다.**
v1으로 계산된 과거 진단은 계속 v1 기준으로 설명됩니다
(`diagnoses.rubric_version` + `input_snapshot`이 그래서 있습니다).

v2에서도 **점수 공개는 백테스트 이후**입니다. 데이터 근거가 좋아진 것과
채점표가 검증된 것은 별개입니다.

## 8. 실측 응답 스키마 (`KorService2/areaBasedList2`)

[OpenAPI 가이드](https://api.visitkorea.or.kr/#/useInforArea)의 인터랙티브 테스터로
**실제 호출한 응답**입니다. 문서가 아니라 실물이라 아래 함정들이 드러났습니다.

### 8.1 응답 구조

```xml
<response>
  <header>
    <resultCode>0000</resultCode>
    <resultMsg>OK</resultMsg>
  </header>
  <body>
    <items>
      <item>…</item>
    </items>
    <numOfRows>12</numOfRows>
    <pageNo>1</pageNo>
    <totalCount>48858</totalCount>
  </body>

```

### 8.2 `item` 필드

| 필드 | 예시 | 비고 |
|---|---|---|
| `contentid` | `2750143` | 콘텐츠 고유 ID |
| `contenttypeid` | `12` `14` `38` `39` | 관광타입 |
| `title` | `가가책방` | |
| `addr1` / `addr2` | `충청남도 공주시 당간지주길 10 (반죽동)` | `addr2`는 빈 경우 많음 |
| `zipcode` | `32549` | |
| `areacode` / `sigungucode` | `34` / `1` | **빈 경우 매우 많음** |
| `cat1` / `cat2` / `cat3` | `A02` / `A0206` / `A02061000` | **빈 경우 매우 많음** |
| `lDongRegnCd` / `lDongSignguCd` | `44` / `150` | **법정동 코드. 항상 채워짐** |
| `lclsSystm1/2/3` | `VE` / `VE12` / `VE120100` | **신규 분류체계. 항상 채워짐** |
| `mapx` / `mapy` | `127.1219749520` / `36.4521187744` | **문자열.** 소수 자릿수 제각각 |
| `mlevel` | `6` | 지도 레벨 |

| `cpyrhtDivCd` | `Type1` `Type3` | 저작권 구분 |
| `tel` | | 빈 경우 많음 |
| `createdtime` / `modifiedtime` | `20260226171412` | `yyyyMMddHHmmss` **문자열** |

### 8.3 구현 함정 8개

**① `resultCode`가 `00`이 아니라 `0000`입니다.**
에러 코드표에는 `00 NORMAL_CODE`로 적혀 있는데 실제 응답은 `0000`입니다.
`resultCode === '00'`으로 비교하면 **정상 응답을 전부 실패로 처리**합니다.
숫자 변환(`int(code) == 0`)으로 비교하거나 `0000`과 `00`을 모두 허용하세요.

**② 필드명 대소문자가 혼재합니다.**
구버전 필드는 전부 소문자(`areacode`, `sigungucode`, `contentid`, `contenttypeid`,
`firstimage`)인데 신규 필드는 카멜케이스(`lDongRegnCd`, `lclsSystm1`, `cpyrhtDivCd`)입니다.
`areaCode`로 접근하면 `None`이 나옵니다. 파서에 필드명을 **그대로** 박아야 합니다.

**③ `cat1~3`이 비어 있는 항목이 매우 많습니다.**
12건 중 6건이 빈 `cat1`이었습니다(음식점·쇼핑 계열).
우리 스펙 §6.4의 "유형별 첫 자원을 먼저 선택"이 `cat1` 기반이면
그 항목들은 **유형 분류에서 통째로 누락**됩니다.
→ **`lclsSystm1`을 1순위로 쓰세요.** 항상 채워집니다.

관측된 `lclsSystm1` 값: `NA`(자연) · `VE`(체험·문화) · `FD`(음식) · `SH`(쇼핑)

**④ `areacode` / `sigungucode`도 자주 비어 있습니다.**
`lDongRegnCd` / `lDongSignguCd`(법정동 코드)는 **항상** 채워져 있습니다.
우리 스펙 §6.2가 "관광 콘텐츠 첫 항목의 법정동 코드로 수요 API 코드를 구성"한다고
했는데, 그 필드가 바로 이 둘입니다. 확인됐습니다.
지역 판별은 `areacode`가 아니라 `lDong*`을 기준으로 하세요.

**⑤ `firstimage`가 `http://`로 옵니다.**
같은 응답 안에 `http://tong.visitkorea.or.kr/…`와 `https://tong.visitkorea.or.kr/…`가
섞여 있습니다. 스펙 §6.4의 "HTTP면 HTTPS로 교체"가 맞습니다.
안 바꾸면 HTTPS 페이지에서 mixed content로 이미지가 안 뜹니다.

**⑥ 요청 파라미터가 `ServiceKey`(대문자 S)입니다.**
공식 호출 예시는 `serviceKey`(소문자)인데 가이드 테스터가 만든 URL은 `ServiceKey`입니다.
둘 다 받는 것으로 보이지만, 실패하면 이 대소문자를 의심하세요.

**⑦ `mapx` / `mapy`가 문자열이고 자릿수가 제각각입니다.**
`127.121658480839`, `127.4341000000`, `126.91894`가 한 응답에 섞여 옵니다.
`float()` 변환 시 예외 처리를 두고, 빈 문자열도 대비하세요.

**⑧ 행정구역 개편 명칭이 섞여 있습니다.**
`전남광주통합특별시`, `강원특별자치도` 같은 표기가 나옵니다.
스펙 §6.2의 "특별자치 표현 제거 후 비교"에 **`통합특별시`도 추가**해야 합니다.
그렇지 않으면 해당 지역 축제의 지역코드 해석이 실패합니다.

### 8.4 파서 방어 코드

```python
# apps/api/src/festaflow/services/tourapi.py

NORMAL_CODES = {"00", "0000"}          # ①

def is_ok(header: dict) -> bool:
    return str(header.get("resultCode", "")).strip() in NORMAL_CODES

def region_codes(item: dict) -> tuple[str | None, str | None]:
    """지역 판별은 areacode가 아니라 법정동 코드 기준."""   # ④
    return item.get("lDongRegnCd") or None, item.get("lDongSignguCd") or None

def category(item: dict) -> str | None:
    """lclsSystm1을 1순위로, cat1은 폴백."""                # ③
    return item.get("lclsSystm1") or item.get("cat1") or None

def image_url(item: dict) -> str | None:
    url = item.get("firstimage") or item.get("firstimage2") or ""
    return url.replace("http://", "https://") or None        # ⑤

def coord(item: dict) -> tuple[float, float] | None:
    try:
        return float(item["mapx"]), float(item["mapy"])      # ⑦
    except (KeyError, ValueError, TypeError):
        return None

NORMALIZE_DROP = ("특별자치도", "특별자치시", "통합특별시",
                  "광역시", "특별시", "자치도", "자치시")     # ⑧
```
